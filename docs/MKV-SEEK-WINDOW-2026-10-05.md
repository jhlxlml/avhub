# MKV 跳播：多短分片供给与下一步方向

构建：`2f7a27c1ffa14037`。本轮不打包、不推送，不修改 E:\downloads 或其他源视频。

## 本轮实际交付

适用路径是 **H.264 MKV + AAC/无音轨的索引按需重封装**；VP9、AV1 等 MKV 原片直放保留原路径，不能把本轮收益泛化为所有 MKV。

- 同一 FFmpeg 按现有索引切出多个短分片，第一片闭合即交付，不等待整个预读窗口完成，不把 HLS 清单临时合并成 10 秒长分片。
- 通常预读约 8 秒，高码率约 4 秒；限制片数、时长和估计字节。开头、长 GOP、超大单片、小缓存等继续走原单片路径。
- 新用户 seek 携带递增版本；分片请求也携带对应版本。相邻取片或重试不递增 seek 版本，过时提示不会取消新版窗口。
- 同一窗口共享生产任务，单个请求断开不取消其他等待者；最后等待者在首片交付前退出则取消。首片 HTTP 正常完成不等于结束后续预读。
- 单会话只有一个实际封装生产锁；取消、退出、失败均唤醒等待者。任务有窗口、时间、日志和缓存边界，仍保留 Windows 进程所有权。
- 发布前检查真实视频 PES 时间戳、IDR 独立起点和清单边界。首视频 PTS 与 DTS 重排延迟分开处理，避免 B 帧或音频定义起点时的偏移。
- 新窗口与已有缓存重叠时不覆盖读者持有的文件；取消后的私有 CSV 和临时片段回收，已打开 HTTP 文件句柄安全释放。
- 异常批量切点仅回退本会话的原单片重封装，不升级为视频转码、不反复尝试失败的窗口。
- 增加分片 `Server-Timing`、缓存命中头、进程/缓存计数及折叠播放信息中的供给统计。剩余客户端耗时并不等于纯解码耗时。

视频、AAC 音频仍用 `copy`。没有修改分辨率、码率、色彩或转码质量参数，也没有缩短客户端的 30 秒缓冲作为“优化”。

## 测量结果与诚实边界

Edge、独立临时数据。源视频只读；真实 H.264 MKV 样本缺失，因此使用真实 H.264 原片的临时无损 MKV 副本，以及有 B 帧、多音轨的合成样本。

| 路径/样本 | 跳播中位数 | P95 | FFmpeg 次数 | 源重载 |
| --- | ---: | ---: | ---: | ---: |
| 合成短 GOP MKV，原单片 | 78 ms | 112 ms | 46 | 0 |
| 同样本，多短片窗口原型 | 81 ms | 134 ms | 22 | 0 |
| 真实 4K H.264 临时 MKV，单片对照 | 274 ms | 324 ms | 47 | 0 |
| 真实 4K H.264 临时 MKV，高码率短窗口 | 262 ms | 343 ms | 27 | 0 |

主要已验证收益是减少重复进程和后续取片开销，并不是单次冷跳播有稳定的大幅加速。小样本 P95 未证明改善，不能称为“全部秒跳”。每组 12 次跳播；系统文件缓存未清空，部分重封装对照与其他测试并行，结果不构成严格隔离的速度保证。

较早版本合成样本连续播放 20 秒实际推进 20.01 秒，持续缓冲 0、源重载 0；随后跳播中位数 75 ms，P95 104 ms。最终版本保留该短 GOP 策略，高码率则缩短预读。

最终构建复测：合成 MKV 连续播放 10 秒实际推进 10.02 秒，缓冲提示和源重载均为 0；12 次跳播中位数 81 ms、P95 130 ms，首帧 308 ms，19 个实际封装进程、56 个已发布短片、80 次缓存命中。仍不把进程减少解释为每次冷跳播都显著加速。

## 更重要的真实 MKV 发现

只读复制索引中的 MKV：766 个 VP9、1 个 AV1，没有 H.264 MKV。因此优先优化当前用户媒体，还应处理原片直放的容器寻址问题。

一段真实约 9.8 分钟、4.1 GB 的 4K VP9 + Opus MKV：

| 测试资源 | 首帧 | 跳播中位数 | P95 |
| --- | ---: | ---: | ---: |
| 原始 MKV | 456 ms | 595 ms | 12687 ms |
| 临时无损 MP4 副本 | 288 ms | 368 ms | 713 ms |
| 临时无损 MKV 副本 | 504 ms | 342 ms | 718 ms |

均由浏览器原片直放、仅一个播放源、保持 3840×2160；临时副本视频与 Opus 音频都使用 stream-copy，没有降画质或重编码。

原片一次跳到约 441.5 秒，测量窗口中接收约 2.28 GB；无损 MP4 同目标约 96.9 MB。这提示存在冗余读取/容器寻址问题，不能只归因于 VP9 解码慢。

无损 MKV 同目标接收约 97.1 MB，类似 MP4；下一步不应简单强制更换所有 MKV 容器，而应先确认并修复索引/寻址的具体差异。

这仍只是一个样本。副本生成已预读源片，原片与临时副本盘位/缓存状态不同；尚未直接解析证明原片 Cues 缺失或损坏。不能把全部加速归因于 Cues，也不能保证所有 VP9 MKV 获得同样效果。接下来应先做同盘同缓存、记录 Range 请求分布及 Cues 的对照。

对应报告：`report-1791184146950.json`、`report-1791187078345.json`、`report-1791188007409.json`。

## 下一步建议

1. **优先针对 VP9/AV1 MKV 原片寻址**：同盘验证 Cues、Range 和真实帧延迟；若证实问题，提供可选、后台生成的无损优化副本，优先保持 MKV、必要时选择兼容 MP4。原片永远只读。
2. 优化副本必须有进度、取消、空间预检、容量上限、失效校验和清理机制。可能接近原文件大小，不应默认为全部媒体复制一遍。
3. 再将重封装索引改为流式，并统一 30/35/90 秒的索引期限；之后增加受播放活动让路的后台索引队列。
4. 补充更多真实 H.264 MKV、长 GOP、VFR、非零起点、不同音轨的重复测试，再决定是否进一步扩大窗口或调整缓冲。

本轮没有实现 VP9 优化副本产品功能，只完成了受控实验；这是下一阶段建议，不是当前应用已拥有的能力。
