# 播放期间批量导入：数据库竞争验收

这是桌面开发迭代的工程记录，不是发布说明。版本保持不变；未打包、发布或推送。
承接 [异常启动、后台收尾与保存长尾核查](STARTUP-MAINTENANCE-AND-SAVE-ACCEPTANCE.md)
提出的“已有视频播放期间批量导入”验证，不涉及已搁置的特定大文件解码问题。

## 本轮改动

- 扫描的目录/媒体快照、单文件索引查询、封面源身份与任务版本预检改走现有
  `read_connection()`。WAL 下读取已提交快照，不占用应用级串行写锁；仍受完整
  数据恢复的独占门保护，不能与库文件替换交错。
- 全新文件无已知路径且无身份候选时，媒体身份服务只读返回“不匹配”。任何
  可能的匹配仍回到原来的文件操作锁和写连接，重新查询、验证后才继承个人数据。
  未放宽硬链接、离线根目录或歧义身份的规则。
- 封面最终更新增加同一 SQL 中的任务版本与 pending 状态条件。即使只读预检后
  等待写锁时任务被替换，旧任务也不能把媒体索引标成已更新。
- 没有把实际写入搬到只读连接，没有延迟/假报进度保存成功；不改 FULL 同步级别、
  自动 checkpoint 或既有关闭/恢复流程，不引入后台媒体转码。

## 可复现负载

`electron/test/bulk-import-playback.mjs` 使用真实 Electron 应用，而非独立浏览器或
独立播放器。默认正常 GPU、sandbox 与 backgroundThrottling，Playwright/CDP 附加。

```powershell
npm run build
npm run build:electron
node electron/test/bulk-import-playback.mjs --videos=1200 --label=local
```

测试创建明确所属的隔离目录与配置：一个已入库的 300 秒 H.264 播放样本，另一个
待导入根目录含 1200 个视频、60 个子目录。真实 FFprobe 探测，没有预构建索引或
模拟扫描。源为 320×180、12 fps、8-bit SDR 的生成视频，不是用户高码率/4K 样本。

1. 打开已有视频，确认实际解码帧与媒体时钟前进，再开始导入另一根目录。
2. 首次扫描约 5%、30%、55%、80% 时暂停，等待应用真实 progress PUT 成功，
   对照暂停时间及随后读出的持久化进度，再恢复播放。
3. 扫描未结束时点击真实“返回媒体库”按钮，核对该次保存成功及实际完成导航。
4. 等待扫描完成与封面队列排空，再重新打开视频并增量扫描全部 1200 个未变文件，
   断言更新数为零。增量任务很快，返回时通常已经结束，不把它冒称为扫描中返回。
5. 正常退出应用，确认后端收尾、WAL 文件实际消失。核对播放样本和模板哈希，
   逐一核对 1200 份导入副本的大小/mtime；不是对全部副本逐一计算内容哈希。

既有播放优先级会让封面解码在播放时让步，暂停和返回后继续排空。因此本轮验证
播放与元数据导入并发、穿插封面工作，不声称连续播放时同时解码全部 1200 张封面。
“扫描耗时”只取任务开始到元数据完成，不包含封面排空和测试动作的全部墙钟时间。

保存耗时包括暂停调用、真实 PUT 响应及随后读取已保存位置；返回耗时包含按钮
操作、该次 PUT 和媒体库可见。不是 SQLite commit 单独耗时，也不是纯磁盘指标。

### 已证明与未证明

- 串行连接操作数约减半是可验证的排队结构变化，不是实际写事务、fsync 或物理
  I/O 次数减半。只读操作增多正是查询移出串行队列，不是消除这些查询。
- 不据一次扫描的几秒差异推导一般提速比例。基线暂停本来就很快；中间构建仍有
  344 ms 保存，不能宣称保存尾延迟已消除或所有操作都更快。
- 中间首轮同阶段存在 AnyIO 线程总耗时 317.981 ms、其中锁等待 312.082 ms，扫描
  线程 commit 最大 398.007 ms。该轮保存记录还没有独立墙钟字段，不把线程记录
  直接当作某个 HTTP 请求的唯一根因。
- 中间重复轮虽然保存较快，后台扫描 commit 仍达 968.270 ms、另一线程锁等待
  958.439 ms。保留这些慢记录；不能仅凭用户操作没撞上就判定长尾已解决。
- 生命周期最大值可能包含初始化或封面排空，不能对最大值做前后相减。操作计数
  与 slow_count 才使用阶段前后差；不同阶段最大值不能相加当成一次请求耗时。

## 并发安全回归

新增 `tests/test_bulk_read_isolation.py` 共 9 项：

- 实际持有未提交的无关写事务时，单文件查询、全库快照、封面预检、新文件身份
  排除都能读取已提交快照，不排在写锁之后；真正封面发布仍必须等待写锁。
- 解码期间任务版本变化、取得写连接前才变化，均不能更新旧封面索引；后一项
  在补上原子 SQL 条件前实际失败，修复后通过。
- 完整恢复持有独占门时，封面只读查询仍等待；不是绕开恢复保护。
- 无匹配的新文件不开写连接；可能的外部重命名仍走原写入校验，保留媒体 ID
  与观看进度。只变更自建测试样本，不操作用户目录。

定向验证：9 项并发隔离、8 项来源身份、20 项封面服务全部通过。

## 最终构建桌面结果

最终构建 **`a20ec98faef6b8f9`** 在原子发布校验补齐后构建，性能负载独立顺序执行，
没有并发跑其他回归套件、修改生产源、强制 GC 或重编译。

| 记录 | 首次扫描 | 暂停保存 ms | 扫描中返回 | 串行 / 只读连接操作增量 |
| --- | ---: | --- | ---: | --- |
| `kYXgNX` / final | 26603 ms | 30 / **258** / 20 / 28 | 154 ms | 4849 / 8589 |
| `gVeyIP` / final-repeat | 26448 ms | 27 / 28 / 25 / 28 | 151 ms | 4871 / 8591 |

两轮均 `completed:true`、`cleanExit:true`、`sourceUnchanged:true`、`walAfterExit:false`，
错误为空；首次各更新 1200 个视频，封面发布累计 1201（包括已有播放样本），
封面任务无失败且排空。窗口显示条件与表中对照相同。

- 两轮首次扫描播放段实际解码均增加 249 帧，waiting/stalled/播放中源重载与掉帧
  均为零；增量段分别增加 20 / 21 帧，事件和掉帧也为零。
- 增量扫描分别 192 / 188 ms、更新均为零，保存分别 25/25、25/24 ms，返回
  153 / 149 ms；两轮返回前增量扫描已完成。
- 首次阶段包含封面排空的墙钟分别 86945 / 86714 ms，不把约 26 秒的元数据完成
  描述为全部封面已生成。播放段也是有限窗口，不等同于长时间流畅性验收。
- 首轮 258 ms 保存的墙钟区间为 1792498568.820–1792498569.078；该区间内有
  AnyIO 线程总耗时 232.158 ms（锁等待 225.370 ms），以及扫描线程 commit
  354.501 ms 的完成记录。时间重合支持继续调查写入竞争，但尚无请求 ID 将
  该操作唯一关联到此 PUT，也没有操作级 fsync/checkpoint 证据，不能精确归因。
- 重复轮没有撞上同等保存长尾，但扫描仍有 260.708 ms 提交。两轮没有发生
  多秒保存，不代表秒级长尾在其他机器、数据库规模或存储条件下已被排除。

结论：本轮可以确认减少无必要的串行读竞争，并保住保存正确性、恢复独占与封面
任务失效保护；**不能宣布数据库提交长尾已根治**。下一步优先把用户保存请求与
数据库操作关联，分辨扫描写入、自动 checkpoint、提交/系统调度的耗时，再评估
写调度策略；不通过降低同步级别或提前返回成功换取表面延迟改善。
