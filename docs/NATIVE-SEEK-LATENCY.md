# MPV 拖动跳播优化与边界

## 实施内容

进度条指针拖动期间只更新滑块和目标时间；松手执行一次原文件精确定位，不再逐个解码拖动途中的临时位置。取消指针或丢失捕获时放弃本次拖动，不误跳播。待定位滑块使用目标位置，直到实际帧完成定位；定位提示未移除。键盘、快进/后退按钮及鼠标侧键仍保留原有精确定位行为。

没有修改 MPV 解码器、缓存、硬件加速、视频/音频质量、精确定位参数或源文件。不改变暂停/播放状态。拖动期间不提供解码画面预览；画面只在提交定位后跳转。

## 尝试后放弃的方案

曾尝试在旧目标未解码完成时，以 33 ms 合并窗口抢占定位。实际 VP9 MKV 收益不明显，而 H.264 TS 连续定位部分变慢，因此已完整回退该生产改动，保持原有 MPV 客户端调度。实验报告：`build/native-seek-latency-F0Qf9T/acceptance.json`；对照基线：`build/native-seek-latency-TUweHR/acceptance.json`。实验构建 `9beae3d67cef4742` 不作为最终交付。

## 尚未解决的部分

单次精确快进/快退本身仍需从前一个关键帧解码到目标。例如本机 4K VP9/AV1 某些目标约 0.6–0.8 秒，此次不宣称其全部变快。MPV 官方说明：[精确定位与关键帧](https://mpv.io/manual/stable/#options-hr-seek)。

若后续增加关键帧快速定位，应作为明确可选项，说明落点可能偏离所选时间；不能自动以牺牲定位精度冒充优化。原画质量原则仍必须保持。

## 后续修复：打开即跳播、时间显示冻结

最终构建 `90863a33ba66cf66`，版本未增加。

- 用只读媒体 ID 2358（4K 60fps AV1 MP4）复现：打开后首帧阶段 `phase=starting` 的立即跳播被直接拒绝。原始失败证据：`build/native-seek-latency-BzcYC2/failure.json`。
- 改为保留启动期间最后一次定位意图，等文件载入且启动指令完成后发出，或在首个重启帧到来时处理。启动状态不提前伪装成 ready；元数据到来后重新限制目标时间，关闭则取消请求。不更改质量或定位模式。
- 组件测试复现：原生滑块键盘操作后失焦，收不到该输入的 keyup，`dragPosition` 一直覆盖真实时钟（实际时钟到 12 秒，界面仍为 10.01）。现在仅指针拖动期间保留本地预览，非拖动输入通过实际播放状态更新，不再依赖 keyup 解除显示锁定。
- 修复校验旧定位时忽略新 `playback-restart` 的时序：记录期间收到的完成事件，校验结束后再检查，避免下一目标长时间悬挂。单元用例覆盖该确定性事件顺序；未恢复之前放弃的激进抢占策略。

## 实际 AVHub 嵌入页面鼠标验收：旧值二次提交

用户反馈前述修复仍无效，因此不再仅凭 `nativePlayer('seek')` 测试判断 UI 正常。使用 computer-use 的 Windows 真实输入，从 AVHub 媒体库封面打开视频，在主窗口内点击/拖动原生控制层；辅助 `native-app-interactive.mjs` 仅启动隔离应用和记录事件/快照，不下发 open/seek/pause 播放指令。原始媒体 ID 2358，只读。

### 新复现的根因

修复前（构建 `90863a33ba66cf66`，`build/native-app-interactive-MCjJZT/timeline.jsonl`）：真实鼠标点击时 input 值为 158.76 秒，画面也开始到达该位置；松手后受控 input 恢复旧时钟 21.69 秒，React 接收迟到的原生 change 又把它作为新目标提交。一次鼠标点击出现两次定位，最终回到约 21 秒。直接调用跳播 API 和仅暂停状态的组件点击没有覆盖这一原生事件时序。前述首帧请求拒绝和本地预览冻结修复不是本次 UI 回跳的完整解决方案。

现在仅 input 事件代表用户的新选择，onChange 不再下发定位；指针拖动用 ref 保存最终目标，松手只提交该值一次，取消捕获不误提交旧 DOM 值。该改动不改变媒体链路、解码、精确定位或画质。
