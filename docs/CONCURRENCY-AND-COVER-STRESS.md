# 并发与真实封面压力验收

## 本轮实现

封面使用一个共享 IntersectionObserver，提前加载视野上下 320px 范围内的图片，移出范围时解除 src 并释放挂载状态。浏览器仍自行管理网络、解码和缓存；不声称移除 src 能立即清空全部缓存或保证固定内存上限。分页规模不变，不用把全库视频塞进 DOM。

返回视野正常重新加载，保留原封面 URL/version 及失败重试规则；收藏、播放预览、片单、列表和深浅色布局不变。最后一张图片卸载时断开观察器，迟到回调不再通知已卸载目标。没有改动视频画质、编码或播放链路。

## 真实封面数据

`node electron/test/desktop-cover-stress.mjs <authorized-library.db>` 将原 SQLite 只读备份到独立 TEMP 配置，仅保留已授权 E:\downloads 的索引，复制应用数据目录中现有封面。源索引、源视频及原封面不修改，不扫描或播放用户视频。原生图片懒加载对照需显式加 `--native-lazy`，只在测试配置禁用视口观察器，不是产品设置。

本机 2178 条真实媒体索引、2178 张现有封面，96 项/页，12 轮分页、60 次快速位置切换：新方案最多同时挂载 12 个图片源，对照 96 个。两次报告中，新方案渲染进程终值约 298 MiB，对照约 324 MiB；JS 堆均经过自然回收，没有据此证明长期无泄漏。测试使用开发版 Electron/软件 GPU 参数，单次顺序测量、缓存和其他进程均可能影响结果，不承诺固定节省比例。

上述内存数值来自隐藏窗口，不作为可见窗口流畅度或固定内存收益的结论。可见且不抢焦点的同条件复测：新方案最多挂载 16 张图片，对照 96 张；两组均无大于 50ms 的 rAF 间隔，无大于 50ms 的主线程长任务（采样最长间隔约 31.4ms）。新方案工作集终值约 654 MiB，对照约 662 MiB，均明显高于启动时约 233/231 MiB，JS 堆首尾约 11.5→10.1/11.8→9.7 MiB。没有认定工作集增长是泄漏，也没有认定已经解决其增长；浏览器解码/绘制缓存、软件 GPU 和 OS 工作集应进一步通过更长滚动及闲置回收曲线分离。不能用 JS 堆下降掩盖工作集增长。

追加的长任务与 rAF 间隔统计包含自动化及分页过程，不作为纯滚动 FPS；报告保留完整采样。原报告在独立 TEMP 的 covers.json，路径由脚本输出，不上传私有视频标题或源路径。

## 并发验收方法

`node electron/test/concurrent-soak.mjs 600` 默认十分钟，可显式传入 60..86400 秒。只生成独立 TEMP H.264 MP4：播放期间周期性新增测试样本、实际启动增量扫描及封面重试；每分钟暂停约十秒，让后台封面继续工作。播放时封面让路是既定保护策略，不为了压测取消它。

采样真实解码帧、掉帧、waiting/stalled、初始首帧之后的 source loadstart、扫描错误、封面发布/失败、JS 堆和 Electron 进程工作集。验收源哈希不变、实际帧推进、无后台引发的源重载、正常退出且本地服务关闭。原生时序与内存数据写入 soak.json；不是隐藏加载提示来判定流畅。

CI 增加一分钟并发 smoke 和视口/观察器回归，发布及失败诊断保存测量报告。CI 一分钟不等于十分钟，更不等于全天候稳定性；合成 H.264 和软件 GPU 结果不能代表实际 4K MKV、TS、长 HEVC 或 HDR。

本机十分钟验收（约 607 秒、60 次采样）正常退出，后端服务关闭；实际解码帧 12671，累计掉帧 18，初始首帧之后 waiting/stalled/source reload 均为 0。封面发布计数 103，扫描错误为 0；JS 堆首尾约 11.9 → 8.1 MiB。保留全部掉帧数据，不宣称零掉帧。源哈希不变，暂停让路窗口刻意存在，不冒称封面解码一直与视频解码同时运行。

首次滚动帧间隔测量出现约 1Hz 隐藏窗口节流，不能作为 UI 卡顿证据。仅关闭测试后台节流仍会被隐藏窗口限制，最终使用不抢焦点可见验收窗口复测；生产窗口节流策略未改动，rAF 统计也不是屏幕呈现帧率。

本轮不打包、不推送，版本保持不变。
