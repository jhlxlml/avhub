# 1080p 大 MP4 原文件直放卡顿核查

日期：2026-10-19。用户明确问题发生在非 MPV 的“原文件直放”。
本轮仅核查及新增隔离诊断入口，没有修改生产播放参数、文件供数、UI、版本或
画质策略，没有打包/发布。其他电脑的实际问题文件、编码、驱动与运行日志尚未
取得；不能把本机对照写成另一台电脑的最终根因。

## 已确认的代码行为

- `Player.tsx` 的现有播放器是 Chromium `<video>`。后端返回 `mode=direct`
  时附加 `/media/{id}/file`；该路径不执行 FFmpeg，不重编码或缩放原视频。
- `media_delivery.py` 使用标准 Range 语义、1 MiB 有界读取，并监听断连以停止
  过时读取。未发现把整个 5 GiB 文件装入内存或对大文件主动限速的逻辑。
- 生产 Electron 没有调用 `disableHardwareAcceleration` 或添加禁用 GPU 的
  参数。不过“GPU 视频解码可用”不代表每个具体文件一定用了硬件解码。
- 播放倍速会从偏好恢复，允许 0.5/0.75 倍；这是用户偏好，不是检测到卡顿后
  自动慢放。核查现场时仍须区分保存的倍速与 1× 下画面丢帧。

## 已确认问题与风险

### 1. 原文件路径查询仍然等待全局串行数据库锁

`app/main.py:media_file()` 用 `connection()` 查询路径，后者持有 `DB_LOCK`。
工程已有 `read_connection()`（WAL 只读连接及恢复读门），但此供数入口尚未使用。
锁在查询结束后释放，不是整个视频传输期间一直持锁；风险是每次新 Range 的
响应开始都可能等待扫描、编辑等写入任务。

隔离临时数据库中，另一个线程持 `DB_LOCK` 400 ms：

| 调用 | 实测等待 |
| --- | ---: |
| 当前 `media_file()` 查询/创建响应 | 401.97 ms |
| 同一条路径查询使用现有 `read_connection()` | 0.72 ms |

这是合成锁竞争诊断，证明依赖关系，不是另一台电脑的播放性能数值。本轮没有
并发扫描，不能将下述丢帧直接归因于这把锁。

### 2. 部分 MP4 可播放，但音视频物理布局不适合 HTTP 随机供数

只读对照索引 ID 725：5,385,420,552 字节（约 5.02 GiB），1920×1080、
H.264 High、8-bit yuv420p、约 29.97 fps，约 123 分钟，文件平均码率约
5.82 Mb/s。不是用户另一台电脑上的已确认问题文件。

FFprobe 只读检查最初约两秒的数据包：

- 视频包偏移约 56–456,995 字节。
- 同期音频包偏移约 5,318,784,708–5,318,792,161 字节。

因此这份文件的同期音视频相隔约 5 GB，并非通常期望的紧邻交织布局。真实
Electron 的末段对照包含四次定位、四组各 15 秒的稳定播放采样，整个诊断累计
1,775 个 Range 响应，全部为 206；相邻请求有 1,770 次跨越超过 64 MiB。
请求明确在视频与远处音频区域往返，增加 HTTP、文件打开和随机读取成本。
在不同缓存/存储/驱动环境下可能放大卡顿，但“布局导致该用户机器慢放”仍待
该文件与该机器证据验证。

此记录也包含成功读取 4 GiB 以上偏移；没有复现该样本的 32-bit 文件偏移溢出。
不能仅移动 `moov` 到头部就宣称解决音视频交织问题，也不能默认对所有 MP4
生成几 GiB 的副本。后续若评估无损重封装，必须复制所有需要保留的音视频轨，
核对时间戳/色彩/附属信息及容量，原文件不改、不自动重编码。

### 3. 目前的诊断与既有通过条件不足以识别“1× 但顿挫”

生产播放信息主要展示首帧、跳播耗时和解码尺寸，缺少具体视频解码器、持续
丢帧、播放时钟/墙钟比、缓冲及供数行为的组合证据。原文件加载成功不等于
流畅；`real-playback.mjs` 原有验收主要排除 MediaError 和 15 秒完全无进度，
没有将实际时钟速率/丢帧作为性能判定条件。

部分既有功能测试禁用 GPU，仅能证明对应交互，不能作为其他电脑的硬件解码
性能验收。无须因此修改生产安全参数或强制跳过 Chromium 显卡限制。

## 建议处理顺序

1. 将原文件供数入口的路径查询与全局写锁隔离，保留恢复/文件变更安全边界，
   加入并发写入时 Range 响应延时及 4 GiB 以上读取回归。
2. 补齐手动导出的原文件播放诊断：实际解码器、GPU/驱动、倍速、墙钟推进、
   丢帧、缓冲、请求数与路径脱敏。用于在问题电脑上判断软解、解码/呈现或供数。
3. 针对证实音视频分区存放的 MP4，先比较有界只读分区预读缓存与无损交织
   重封装的实际收益，控制内存/磁盘预算，不默认复制所有大视频、不改原片。

没有问题电脑日志前，不强制显卡、不添加 `ignore-gpu-blocklist`、不增加全局
巨大缓存，不通过降帧/降清晰度/转码或隐藏等待提示宣称修复。
