## 实现与可靠性

此前新文件的媒体元数据提交成功后，才另开事务写入封面待办。现在真实桌面
ThumbnailService 的扫描路径在同一 SQLite 事务中更新媒体元数据并写入待办。
这也避免提交媒体记录后立即中断，留下没有对应封面待办的窗口。

- `ThumbnailJobs.schedule_in` 接受现有事务，不自行提交、不唤醒工作者，沿用
  指纹、pending 去重、失败冷却、修订生成和显式重试优先级/指定时间等规则。
- 扫描持有封面发布门后才进入写队列，与封面发布、暂停/文件变更同一锁顺序；
  FFprobe 和视频解码不在该门或写事务里。事务成功退出后才唤醒封面工作者。
- 入队/commit 失败，媒体技术信息与待办一起回滚，不发出成功唤醒。取消在获得
  写锁后、事务结束前复查，避免等待期间收到取消却仍发布半项结果。
- 新元数据保存获得写锁后再核对源身份，拒绝等待期间已变化的源。扫描不修改
  标题、收藏、进度或自定义封面；扫描引起的任务新修订不会被旧完成回执删除。
  这次文件属性核对计入事务体耗时，不是“临界区完全没有文件 I/O”的承诺。
- 未变化但重新上线/重新归属目录的媒体，如同时缺少封面，也在修复元数据的
  同一事务中入队。没有元数据修改的补封面仍沿用独立入队，不凭空新增写入。
- 保留同步/组件队列的原 submit 接口；真实产品的扫描使用持久桌面服务。
  独立补封面、显式重试和已有封面任务完成路径不被改成批量扫描事务。
- 保留 FULL、默认自动检查点、WAL 生命周期与保存优先门，不改表结构或设置。
  每个文件各自提交，不积累巨型事务，不改变视频解码、画质、位深或色彩。

该原子性仅涉及同一数据库里的媒体信息与待办；不意味着 FFprobe、文件系统、
JPEG 发布也加入跨文件事务。不做真实断电保证，也不缩短操作系统写盘等待来
伪造收益。

## 测试边界

新增 11 项隔离数据库测试，探测/解码使用明确的 stub，仅验证语义与故障恢复：

- 新媒体与任务一次持久提交，计数包含原有技术信息/归类及新任务，无第二次 submit。
- 入队失败、commit 失败、入队后取消均整体回滚；之后重扫可成功。
- 唤醒时重新打开数据库可读到已提交的两项；新服务可恢复持久任务。
- 技术刷新保留用户信息、已有 pending 修订；刷新失败回滚此前元数据及任务。
- 缺失源重新上线与补封面合并，失败冷却/指定帧重试不被扫描覆盖。
- 任务源指纹变更得到新修订，旧完成不能删除；明确排队等待写锁时取消或
  源变化不保存旧结果。

真实 Electron 验收另外使用真实 FFprobe/FFmpeg 和正常 GPU/sandbox，不使用
上述 stub；性能测试与后端/UI 回归分开运行。开发构建标识为 `f90a94063cca38d3`。

两轮首次扫描约少 3.6–3.9 秒，含封面总墙钟约少 4 秒，表明收益不仅是隐藏提示。
历史对照不是本轮随机交错重跑，不推广固定提速比例。极值虽低于上轮，仍有
约 127–133 ms 提交，不能据此声称偶发长尾已根治。

特别注意：数据库 lock_wait **不包含获取封面发布门的等待**。本轮将扫描纳入该
门，因此数据库锁等待数值下降不能证明端到端排队等比例下降；事务 commit
计时边界未变。端到端扫描、实际暂停保存与返回另行保留，不用“排队挪位置”
作为改善证据。后续应补齐门等待归因，而非仅看这一个指标。

- 新轮首次暂停保存 23/23/18/24 ms、27/17/25/27 ms，返回 131 / 144 ms。
  增量扫描 227 / 223 ms、更新均为 0；增量暂停 23/25、32/24 ms，返回 148 / 149 ms。
  保存相关响应均关联实际 committed 数据库操作，进度重新读取一致。
- 活动解码帧首次各增加 214、增量各增加 21；观测开始后掉帧、waiting、stalled、
  意外重载为 0。首次帧增量比上轮少，是扫描更早结束、按进度采样更早返回的
  观测窗口变化，不当作解码帧率提升或下降。
- 两轮 completed / cleanExit / sourceUnchanged=true，errors 为空，封面排空，
  正常退出后 WAL 不存在；私有 SQLite verified=true。源模板/播放源核对 hash，
  导入副本核对大小/mtime，而非对每份副本 hash。
- 所有源为生成的 320×180 / 12fps / H.264 SDR / 静音样本，不能证明用户真实
  4K/HDR、高码率、音频设备、MPV 或多屏兼容性，也不代表搁置视频问题已修复。

## 持续桌面操作

独立第三轮证据：`build/desktop-usage-avhub-desktop-usage-OGRbnf/soak.json`。

- 实际 189.127 秒、17 轮操作、51 次真实静音预览，活动帧增加 805；活动掉帧、
  waiting、stalled、意外重载均为 0，最大返回耗时 154 ms。
- 初次扫描及后续新增源合计 606 个：scan-media 为 606 次 / 2424 项行变化；
  封面重试使 cover-publish 为 630 次 / 1260 项行变化，cover-queue 为 7 次 / 0 项。
  既没有独立扫描入队写入，也没有成功发布后的第二次完成删除。
- 最大 commit 113.499 ms 来自 cover-publish；scan-media 最大为 95.355 ms。
  progress-save 最大 commit 3.311 ms、数据库锁等待 0.430 ms。未测量发布门等待，
  不从数据库锁等待较小推导所有排队很小。
- completed / cleanExit / sourceUnchanged=true，errors 为空，私有 SQLite
  verified=true，退出后 WAL 为 0 字节；运行期观测最大 WAL 4210672 字节。
- 正常 GPU/sandbox/后台节流；内存仅按周期取样。三分钟不等于数小时稳定性，
  不证明无泄漏、冷盘、多屏或真实高码率样本表现。全过程未更改生产代码。

## 下一步建议

先补齐封面发布门的等待次数、耗时和端到端关联，让排队迁移可观察；再针对
检查点与慢 commit 做单独实验。保留 FULL 和当前默认策略，取得多轮实证后再
决定是否调整检查点，避免把写盘长尾迁到退出阶段，或以可靠性换吞吐量。
当前两个重复提交窗口已合并，不继续将多文件堆成巨型事务。
