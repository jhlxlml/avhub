# MPV 状态、关闭恢复与跳播协调

## 范围

本轮落实项目核查中的第一批问题：关闭后状态恢复、片尾连播判断、独立 MPV
跳播状态与短时后台读取优先级。未打包、未发布、未提升版本；未改冻结网页版。

保持原文件直读、原分辨率、既有 GPU/硬件解码与精确跳播参数。没有重新编码、
色彩转换、降低缓存质量或隐藏缓冲提示来改变验收结果。

## 修复原则

### 播放器退出与保存失败分开

- MPV 正常 Q/X 退出会卸载时间及轨道属性。`MpvClient.playbackProperties` 保留
  卸载前的最终保存快照，和实时 `snapshot.properties` 分离；不会用保存的旧时钟
  证明视频仍在播放或新画面已经解码。
- 内嵌与独立模式的进度保存均读取这一保存视图。独立模式最后一批写入等待全部
  任务落定，避免首个失败遮住尚未完成的其他设置写入。
- 保存失败不再阻止确认已经退出的原生进程和清理它的文件读取保护。只有进程
  确认退出后才释放读取租约；退出未确认仍保留保护，不能借保存失败绕过。
- 保留未保存快照，媒体库明确显示“播放窗口已关闭”，提供“重试保存并关闭”及
  经应用确认框确认的“放弃未保存进度”。后者不删除视频或已有数据库记录。
- 清理失败也保留可重试会话。尚未成功启动的失败会话继续支持启动清理重试，
  不要求获取一个根本没有返回前端的会话 ID。
- 保存错误恢复后清除对应提示；不再把未知通知事件当成下一条播放操作。
- Q 与自绘关闭按钮先在 MPV 内发布关闭意图，再立即退出，避免正常关闭的管道
  断开被误报为连接失败。意图不是退出证据，读取保护仍等待 OS 进程退出。
  无请求的传输异常和非零进程退出仍保留错误判断。

### 独立 MPV 保留原生输入路径

- 自有 Lua 控制器先发布固定格式的目标意图，然后在 MPV 内直接设置 `time-pos`。
  不通过 React 或额外渲染窗口往返执行定位。进度拖动仍只在释放时提交一次。
- 连续相对跳播基于尚未完成的最新本地目标累加，而不是反复读取旧播放时钟。
- Electron 观察目标修订、`playback-restart` 与实际 `time-pos` 查询，完成后记录
  `lastSeekTarget`、`lastSeekPosition`、耗时。旧查询不能确认新目标，ACK 本身不是
  解码成功证据。未能确认的目标有 15 秒上限，并支持下一次输入重试。
  原生观察耗时从 Electron 收到意图起算，不包含物理键鼠到 MPV 的前段延迟。
- 对未经自有控制器发布目标的原生定位，目标准确度为未知，不凭当前时间猜目标。
- 独立输入的观察逻辑不额外注入 demuxer 纠偏参数，避免与 MPV 本地队列成为
  两个执行控制者。既有应用协调式跳播的有界纠偏保持不变。
- 暂停定位也报告短时 preparing/playing 读取优先级，状态变化即时更新、心跳
  续期；活动请求合并为一个在途请求加最新状态，最终 inactive 不被旧心跳覆盖。
  这只证明调度信号正确，不等同于物理硬盘 I/O 提速。

### 不按“最近一秒跳过”吞掉自然结束

使用目标是否到达末端、暂停意图及实际时钟推进区分手动末尾定位和自然结束。
正常播放跳至片尾前不足一秒后自然结束，仍由 AVHub 队列触发连播；暂停定位到
结尾不擅自切片。未改变画质、加载来源或自动转码权限。
