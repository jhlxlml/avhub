# 有界扫描批次提交：隔离实验

后续实际桌面扫描观测见 [真实扫描就绪验收](SCAN-READINESS-ACCEPTANCE.md)；
以下保留纯数据库实验结果，不替代桌面验收。

承接 [发布门与检查点归因](PUBLICATION-GATE-AND-CHECKPOINT-ATTRIBUTION.md)。本轮只
增加实验工具与测试，**没有修改生产扫描、设置、API 或播放路径**，没有启用
批量扫描默认值。FULL、默认自动检查点、保存优先和发布门顺序均保留。
未访问日常媒体库或 `E:\downloads`；不打包、不推送、不升级版本。

## 工具边界

`scripts/benchmark-scan-batches.py` 创建自己的临时媒体库与 1200 个占位文件，
复用项目真实 schema/index、connection、WalAnchor、SavePriorityLock、
ThumbnailService.scan_write、series assign、thumbnail_jobs.schedule_in 和
save_progress。实验写入逻辑在脚本中，**不是 scan_file，不是产品扫描器**。

- 每次运行写入 1200 条媒体记录及 1200 条 pending 封面任务；工作者未启动，
  不解码/发布封面。媒体四项行变化共 4800，另有固定 24 次观看进度写入。
- 使用预设合成技术元数据、不可播放的自建占位文件。没有真实 FFprobe、目录
  遍历、来源身份审核流程、Electron、解码帧或播放观测，不声称原画播放改善。
- 活动批次最多 8 条，文件属性/标题准备在事务前；事务内验证属性未变。源身份
  是设备/文件 ID/大小/mtime_ns 指纹，不是内容 hash；相同指纹不保证内容相同。
  实验结束另外逐份 hash、大小与 mtime 核对源没有被工具改动。
- 固定顺序 1 → 4 → 8 → 8 → 4 → 1，每轮新库同源，非随机化或冷缓存 A/B。
- 每轮 24 次实际 save_progress 调用由另一线程按已提交数量触发，不伪造保存
  响应、不在事务内人为等待采样。各轮保存次数相同，但到达时间、竞争时机不同。
- 调用成功只在整批 commit 后返回 ID、唤醒工作者、增加 processed；取消或任一
  条写入/提交失败整体回滚。已提交后取消以已持久化结果为准，不虚报回滚。
- 全部行数、pending 数量、最后观看进度及 integrity_check 均核验，anchor 关闭
  后无残留 WAL。临时库自动清理，只留工程 build 下的无源路径性能记录。

## 六轮结果

证据：`build/scan-batches-1792563891556608900/report.json`，SQLite 3.54.1，
completed=true / source_unchanged=true。使用固定私有运行库包装入口，性能运行
期间没有并发其他回归或性能测试。

| 顺序/批大小 | 元数据提交次数 | 实验写入墙钟 ms | 保存中位数 ms | 保存 p95 ms | 保存最大 ms | 扫描 commit 最大 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 / 1 | 1200 | 7558.502 | 10.676 | 15.559 | 111.181 | 94.753 |
| 2 / 4 | 300 | 2165.440 | 5.795 | 6.384 | 6.422 | 6.004 |
| 3 / 8 | 150 | 1201.323 | 5.537 | 7.428 | 7.767 | 6.122 |
| 4 / 8 | 150 | 1395.686 | 5.592 | 7.843 | 9.194 | 198.293 |
| 5 / 4 | 300 | 2110.797 | 5.543 | 6.456 | 6.706 | 5.727 |
| 6 / 1 | 1200 | 7504.435 | 10.726 | 13.252 | 13.440 | 107.025 |

表中“实验写入墙钟”是预设元数据的准备与批次持久化，不是完整视频导入。
所有轮次媒体数据项、封面待办与 24 次保存均保留，24 次保存都在扫描结束前
发起，含最后等待保存结束的 all_work_ms 与扫描墙钟相差不到 0.02ms。
每轮最后关闭 anchor 约 3.8–4.6ms。

提交次数少是有真实数据库收益的，不是省略行或降低 FULL；但不能把纯数据库
7.5 秒 → 1.2 秒换算成应用整体快六倍。真实探测、封面发布、播放并发、批次
凑齐等待以及生产身份/权限协调均不在这段纯写入数据里。

第四轮 8 条批次仍有 198.293ms commit、202.327ms 门内持有；采样保存最大却
只有 9.194ms，说明这些保存没有撞上最慢那一批，**不能从采样保存较快推导
最坏保存等待被限制在 10ms 内**。这也不证明长尾由批次大小导致，或 4 条就能
避免长尾。保存优先不能打断已经持有写锁的事务。

## 功能验证

新增 12 项隔离测试，解码未参与，不作为性能数字来源：

专项 12 项通过，2.028 秒；随后完整后端回归 545 项，544 通过、1 跳过，
98.757 秒。性能六轮结束后才运行该回归，没有并发干扰上述性能数据。

- 一批八条一次提交，唤醒后重新读取到全部媒体与待办；输入上限在写入前校验。
- 事务前取消、写入部分后取消、第三条入队故障、commit 失败均无部分落库。
- 后面的源属性变化导致整批回滚，恢复或剔除失败项后可重新处理。
- 重新创建工作者后重放不重复创建媒体和 pending 修订；原 pending 修订保留。
- 技术刷新保留用户标题、收藏、进度和自定义封面，旧完成不能删除新任务修订。
- review 来源不被复活；提交后取消不抹掉已完成结果。
- 强制当前批次仍持有写锁时排队保存，验证它不能抢占当前批次，但先于下一批
  持久化。该测试人为阻塞仅验证排序，不混入上述性能结果。

## 决定与下一步

**本轮保留逐条提交默认行为。**纯数据库实验值得继续，但尚不足以让产品默认
采用 4/8 条批次。当前生产是最多两个扫描工作线程，探测和写入都在同一个
文件工作任务里，并不存在持续积压四或八条“已探测就绪记录”的独立写入队列。
强行等待凑批会延迟首批可见结果，还需要解决慢探测、单项失败隔离和取消后的
准确进度，不能直接套实验工具。

下一步先测真实探测完成后的就绪积压和等待分布，再决定是否做最多 4 条的
机会式合并；只合并已经就绪的项目，不为了凑满额外等待。候选方案仍须通过
真实 Electron 播放/扫描并发和持久保存对照，明确未改善或退步就不采用。
本轮没有新的 Electron 构建/验收，不将隔离工具当作桌面验收；生产源码构建
标识仍为上轮 `ebae7e0960d90e45`。

## 复现

```powershell
python scripts/python-runtime.py -m unittest discover -s tests -p test_scan_batch_experiment.py -v
python scripts/python-runtime.py scripts/benchmark-scan-batches.py --videos=1200
npm run test:backend
```

CLI 只允许自建临时库，不能指定日常媒体目录或数据库路径。`--videos` 仅为
合成记录数，限制 384–2400，不是从用户目录读取视频。
