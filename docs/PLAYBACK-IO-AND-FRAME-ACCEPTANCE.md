# 保存 I/O 与帧呈现专项

本轮是桌面本地迭代，不升版本、不打包、不发布。生产构建标识为
`fd7959ba4e0d1df9`。没有访问或改动用户视频；测试源均为隔离生成样本。
此前搁置的约 5 GiB 问题视频不属于本轮修复范围。

## 已实施

- 当前页封面优先级改为最多 120 项的临时内存提示，不再为页面切换写数据库。
  持久任务、源身份、重试时间、指定截图时间和修订号仍保存在 SQLite。
  明确重试的持久优先级仍与页面提示按时间竞争；重启只丢临时提示，不丢任务。
- 封面工作者的任务选择、计数及目录查询改走受保护的只读连接，不再排队占用
  进度写入互斥锁。恢复备份时重载暂停设置仍使用可重入串行连接，不能从独占
  读门禁内再次申请普通快照读；恢复后清空旧页面提示。
- 根目录激活时只更新确实处于延迟状态的封面任务，避免把本来为零的延迟再写一遍。
- Chromium 播放器的暂停、返回、切换和关闭若碰上**同一份、最新且尚未完成**的
  进度保存，共用该次请求。不同进度仍单独保存；完成和失败的请求不缓存。
  keepalive 不复用普通 fetch，保留卸载保护、单调时间戳和旧响应防覆盖逻辑。
  导航仍等待服务确认，SQLite 同步/提交级别和保存期限没有降低。

## 功能验证

- 后端全量 420 项：419 通过、1 项明确跳过，约 129 秒。
- 第一组 renderer/HTTP 契约回归 23 项通过，约 56 秒，包含新进度合并、失败后
  原地重试、完成后重新确认保存、keepalive、晚到旧响应、退出和封面任务。
  这些是隔离组件/接口测试，不是桌面验收。
- 连播、目录/队列导航和播放稳定性另 53 项 renderer 回归通过，约 2.2 分钟。
- 封面专项包含连续 300 次页面优先级更新零数据库连接、最多 120 项内存、任务
  重启恢复、离线等待、修订保护及写事务未提交时工作者仍能只读选取任务。
- 帧证据纯契约核对了启动掉帧不丢弃、互不重叠时间桶、首次加载与播放中重载的区别。

## 帧呈现对照：不是零掉帧验收

正常窗口策略（背景节流开启、sandbox 开启）下，对生成的 H.264 SDR、640×360、
12/60 fps 无音轨 MP4 采集 `requestVideoFrameCallback`、质量计数、页面动画间隔、
媒体时钟和 long task。启动计数完整保留；按首次 `play()` 之后 0–1、1–4、4–8、
8 秒至结束分别记录。不修改原文件或播放参数，不隐藏缓冲提示。

完整 CDP 对照：`build/frame-probe-avhub-frame-probe-Ngv1F2/frames.json`。

| 视频 | 文档 | 悬停预览 | 总帧 / 掉帧 | 动画回调中位间隔 |
| --- | --- | --- | --- | --- |
| 12 fps | 实际播放页 | 关闭 | 151 / 12 | 18 ms |
| 12 fps | 实际播放页 | 开启后打开 | 149 / 10 | 18 ms |
| 12 fps | 极简视频页 | 无 | 149 / 11 | 18 ms |

极简页与实际页使用同一 Electron 窗口、来源和解码链路，但没有 React、控制栏、
滤镜和应用变换。六组均无播放中源重载，未观察到 renderer long task。
系统报告的显示器为 60 Hz、175% 缩放；18 ms 是实测页面调度间隔，**不是**对
物理显示刷新率的改写，也不能单独证明驱动、显示合成或解码器某一个有问题。
短测、窗口尺寸、系统负载和测量开销限制了归因，不能据此宣称 UI 完全无成本。

前一无调试器记录 `build/frame-control-avhub-frame-control-WaDxNi/frames.json`
同样复现：12 fps 为 150 / 12，60 fps 为 729 / 122，页面动画中位间隔约 18 ms。
该次在 60 fps 的“回调数必须超过 480”断言处失败（实际 479），没有完成最终
返回验收。保留失败记录，不把它计作通过；帧回调可能晚到或错过，应保留这些
坏样本。后续测量的完成条件检查真实解码和媒体时钟推进，不再把回调数量门槛
当作流畅通过条件。完成测量与达到流畅目标明确分开。

修正测量条件后的无调试器完整记录：
`build/frame-control-avhub-frame-control-q2cWa9/frames.json`。
`completed:true`、`cleanExit:true`、`sourceUnchanged:true`、错误列表为空。
12 fps 为 149 / 10，60 fps 为 728 / 121，均无播放中源重载；掉帧仍然存在。
两组均验证了人为重叠的暂停/返回只有 **1 次真实 PUT 保存**，且服务响应成功。
这里的完成/退出标志只确认测量及功能验证结束，不是零掉帧通过结论。

## 短组合复测

`build/desktop-usage-avhub-desktop-usage-eMsjII/soak.json`：192 个生成视频，实际
129.692 秒、12 轮、36 次真实解码悬停预览，穿插增量扫描及封面重试。
正常 Electron 窗口策略；没有并行运行其他回归套件。
`completed:true`、`cleanExit:true`、错误列表为空；代表源样本哈希/大小/修改时间
不变（不是对全部衍生副本逐个做哈希验收）。

- 返回中位 103 ms、最大 525 ms；总帧 664、掉帧 49、waiting 1、stalled 0、源重载 0。
  仍保留掉帧和缓冲，未将其认作“已经流畅”。
- 最近 512 项数据库采样：只读 353、串行 159；串行提交 p95 6.723 ms、最大
  435.803 ms，串行总耗时最大 440.991 ms，关闭连接最大 4.678 ms。
- 先前同规模正常策略短测 `QRZnOv` 的返回中位 101 ms、最大 108 ms。
  本轮**没有证明返回延迟变快**，且多了约 436 ms 的提交长尾；不能隐去坏样本，
  也不能用两次短测便将差异归因于此次代码或判定负优化。
  同为最近 512 项的串行/只读计数从 237/275 变为 159/353，符合调度读取改走只读
  的方向，但这不是整个运行的事务总数、物理 I/O 数或“性能提升 33%”。

这次没有复现十四秒保存等待，不代表二十分钟偶发长尾已经根除。

### 可复测入口

先运行 `npm run build`、`npm run build:electron`，不要边测试边改生产源或重新编译：

```powershell
node electron/test/playback-frame-probe.mjs
node electron/test/playback-frame-control.mjs
node electron/test/desktop-usage-soak.mjs --seconds=120 --videos=192
```

第一项是六组 CDP 对照；第二项不挂 Playwright、inspector 或调试端口，仅由主进程
驱动真实 UI。第二项在帧采样结束后才人为延迟保存响应 200 ms，验证暂停/返回
只发一笔真实保存；这段人为延迟不计作性能测速。所有样本和配置均由入口独立创建。
不要同时运行其他回归套件来解释帧率或 I/O 的变化。

早期 `wqGTP4` 因生产源已经变化而静态 UI 尚未重编译，被既有构建一致性保护拦截；
`Rsd4wj` 将极简页首次 `loadstart` 错当重载而中断。两者保留为未通过记录，不合并
进完整对照。后续按首次 playing 区分初始加载和真正的播放中重载。
