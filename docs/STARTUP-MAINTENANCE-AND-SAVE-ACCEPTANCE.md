# 异常启动、后台收尾与保存长尾核查

本轮仅桌面源码迭代，版本不变；不打包、不发布、不推送。原视频没有执行修改、
删除或转换；测试使用隔离配置、生成样本及明确所属的测试进程，不纳入搁置项。

## 修复范围

### 启动失败收尾

- 后端就绪后若窗口创建失败，启动错误处理现在先标记正在退出，再等待所属后端
  的既有有界关闭流程，最后显示错误并退出。避免直接 `allowQuit` 绕过后端清理。
- 启动超时不再先杀父进程；由错误收尾统一处理完整所属进程树，避免先丢失父子
  关系后才尝试清理冻结后端的子进程。
- `spawn` 失败或进程被信号终止可提前结束就绪等待；不存在所属 PID 时不发关闭
  HTTP 请求或等待退出期限。保留 45 秒就绪期限和原有关闭期限，不扫描或清理
  其他应用进程，不引入关闭任意 PID 的前端接口。
- 清理失败/未确认保留日志；`startup-cleanup-complete` 表示收尾尝试结束，不凭此
  单条日志认定进程已退出。真实测试另核对进程、子进程及健康接口不可达。

### 后台维护与退出

- 两个既有十秒维护步骤分别隔离普通异常，某一步失败不阻断同轮其他步骤或永久
  停止定时循环。下一周期仅重试原有幂等维护，不重放文件操作、设置或保存请求。
- 部分启动失败、取消请求失败、单组件关闭失败时，仍尝试其余组件的清理。
  保持先发送扫描/封面取消，再关闭各资源所有者，最后由外层释放 WAL 空闲连接。
- 工作者在自身 join 期限后返回 `False` 不再被当成关闭成功。全部清理尝试后统一
  报告失败；不把仍运行的线程标成已关闭，不使用线程强杀或修改持久化级别。
- `service_lifecycle` 诊断有界保留步骤计数、当前/最近错误类别及恢复时间。
  不包含错误正文、源路径或 SQL；同一步警告限频，成功后清除当前失败状态但保留
  历史失败次数。`CancelledError` 不当作普通失败吞掉。

### 保存长尾证据

最近 512 条数据库操作仍保留原口径。另增加全程（进程本次运行内）的有界计数、
各阶段最大耗时及最慢 8 项，避免早期慢提交被后续快速请求或最近 32 项慢记录
覆盖。新增统计不额外写磁盘，不保留每条 SQL，不将滚动 p95 冒充全程 p95。
组合测试记录初始化结束快照与工作负载开始时间，区分早期扫描和重复播放阶段。
以上是归因能力，不是声称已消除长尾。

## 验收方法与限制

- 新增后端故障回归覆盖部分启动、维护失败后恢复、同轮维护隔离、多个关闭失败、
  未完成的工作者、主体异常/取消及 WAL 释放；另验证全程统计不会丢失早期坏样本。
- `startup-failure.mjs` 在真实 Electron 内，通过测试入口注入窗口创建失败；还测试
  不存在的开发运行时和不提供健康接口的真实所属进程树。未给生产入口添加测试
  开关。错误框用替身避免无人值守阻塞；后台服务与树关闭是真实执行。
- 正常退出、窗口、迁移、保存/备份/封面接口须另回归。渲染器/HTTP harness 不替代
  桌面验收；合成媒体长测不代表所有真实格式、冷盘或物理屏幕验收。
- 单次组合负载完成不等于没有掉帧/长尾；只计算实际解码、保存响应及完整退出。

```powershell
python -m unittest discover -s tests -p test_service_lifecycle.py
python -m unittest discover -s tests -p test_db_timing.py
node electron/test/startup-failure.mjs
node electron/test/shutdown.mjs
node electron/test/desktop-usage-soak.mjs --seconds=1200 --videos=600
```

测试前先运行 `npm run build`、`npm run build:electron`，不要在运行期间改生产代码或
重编译。性能负载单独串行运行，不与完整回归套件并发。

## 独立二十分钟结果

上述最终构建独立运行 **1203.728 秒、108 轮、324 次实际解码悬停预览**；600 个生成
视频起步，穿插发现新文件、增量扫描及封面重试，缩略图发布计数最终 780（包含
重试，不是 780 个不同文件）。没有并发运行其他回归套件，没有中途修改生产源、
重编译、强制 GC、清缓存或替换视频质量。

- `completed:true`、`cleanExit:true`、`sourceUnchanged:true`、错误为空。源身份核对
  代表性生成文件的哈希/大小/mtime，不是对全部 600 份副本逐一验收，更不是用户
  原视频的覆盖性测试。
- 实际保存响应成功后返回媒体库，中位 **145 ms**、p95 **181 ms**、最大 **243 ms**。
  没有提前离开或假报保存成功。不是拿新窗口/显示条件与旧短测计算提升百分比。
- 初始 ready 之后的播放段合计 5117 帧、3 掉帧，waiting/stalled/播放中源重载为零。
  初始加载不在此区间；不以等待事件为零声称完全流畅。
- 窗口保持生产的工作区内启动尺寸；初始及每轮 Electron 显示报告均为 175%、
  32 Hz。这是 API 采样值，不是物理刷新率连续测量；生成源是 12 fps、320×180 SDR，
  不能与 60 Hz/60 fps、不同窗口或真实高分辨率样本直接比较掉帧。
- WAL 最大观测值 **4,206,552 字节**，只是每轮观测最大值，不是容量上限或每一瞬间
  峰值。正常退出后 WAL 文件实际不存在；桌面日志确认 `backend-stopped gracefully`
  后 `shutdown-complete`，不是仅关掉窗口就当作后端退出。
- 维护阶段两步骤各执行 124 次，失败计数均为零；这包括正式循环开始前的准备
  时段。退出步骤在最终诊断快照之后执行，其结果另由退出回归和桌面日志核对。

### 数据库阶段归因

全程统计保留了初始化阶段最慢的 8 项，最终与初始最慢记录一致，没有被后续快速
请求覆盖：串行提交最大 **354.295 ms**、锁等待最大 **354.472 ms**、单次操作总耗时
最大 **359.882 ms**。这些最大值不一定属于同一操作，不能相加当作某次实际等待。

基线到最终诊断新增 5364 次串行连接操作、4880 次只读连接操作；两组均未新增
总耗时 ≥100 ms 的记录。串行操作不等同于实际写事务、fsync 或物理 I/O 次数。
最近 512 项中串行提交 p95 2.616 ms、最大 51.268 ms，串行总耗时最大 52.262 ms；
这是尾部窗口，不冒充全程 p95/最大值。

本次没有复现旧记录约十四秒保存等待，支持当前构建在本负载下的响应和收尾稳定；
**不据此关闭所有偶发长尾**。此前合成 FULL/WAL 对照仍有秒级提交，物理存储与
系统调度未完全隔离。下一步应针对“已有视频播放期间的大批量导入”复核剩余串行
只读检查与用户保存竞争，而不是降低同步级别、减少保存确认或隐藏等待提示。

批量导入的后续核查与限制见
[播放期间批量导入：数据库竞争验收](BULK-IMPORT-PLAYBACK-ACCEPTANCE.md)。
其中保留了中间轮次的保存/提交长尾，不能以快速轮次覆盖它们。
