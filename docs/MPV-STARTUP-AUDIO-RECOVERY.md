# 原生首帧判定与音频输出故障恢复

## 实际故障证据

前一轮 4K 首次打开的偶发失败已再次通过实际 Electron 入口复现。报告：
`build/native-presentation-performance-dprrax/failure.json`，构建
`25111127aed2e33e`。只读样本为已授权目录中的 ID 196（3840×2160 VP9 MKV）。

有限的原有协议事件显示：`start-file` → `file-loaded` → `playback-restart` →
`end-file(reason=error, file_error="audio output initialization failed")`。
当时没有持续播放的时钟证据，但旧实现已记入约 456 ms 的 firstFrameMs。
后续构建 `5e22ee4c59f77f14` 的
`build/native-presentation-performance-GuPl7T/failure.json` 再次捕获同类失败：
视频重启信号与有限时钟可以先于音频失败出现，firstFrameMs 约 475 ms。
这可能是真实视频输出的先行信号，不能因此认定音视频均已准备完成。

因此能确认：这次失败发生在音频输出初始化，不是仅凭“4K 打不开”就能认定的
硬盘瓶颈或视频解码能力问题；旧实现把视频首帧信号等同于音视频就绪。原文件可被只读
FFprobe 正常探测，同一版本曾完成有日志和无日志的播放/定位。

目前并未确定 Windows 音频设备失败的具体原因（设备切换、驱动、系统端点状态等），
也没有修改或重启系统音频服务、改变默认输出设备。不能把应用错误处理修复写成
“Windows 音频设备故障已经根除”。

## 修改

1. `firstFrameMs` 记录同一已加载文件的视频重启信号、有效视频尺寸与有限播放
   时钟共同成立的时间，不把它冒充桌面合成/像素显示延迟。`readyMs` 另记音视频
   输出就绪时间：还需选中视频轨道的信息；若选有音轨，则必须观察到有效
   `current-ao`，不能把缺少输出或 null 输出算作成功。无音轨/明确关闭音轨不
   额外等待音频。属性较晚到达仍可完成判定，没有增加固定等待或起播重载。
   空闲重启、元数据、IPC ACK 不独立证明就绪；失败后迟到属性或卸载 EOF 不能
   恢复失败会话/触发自然连播。超过 30 秒的提示也改为音视频尚未就绪。
2. 使用结构化 `end-file.file_error` 分类为音频输出、视频输出、来源、解码或未知。
   只向应用状态导出固定 failureCode 与中文提示，不导出任意原始字符串/路径，
   不解析易变的解码日志来控制生产行为。
3. 音频输出失败提示检查 Windows 声音输出设备并重试；不自动选择 null 音频、
   关闭音轨、降低分辨率、转换音视频或切换 Chromium。保持既有原文件、精确
   跳播、GPU 后端及硬解设置。
4. 媒体库提供明确的“重试原生播放”；内嵌视频叠层也提供同名刷新图标，视频
   全屏时不必先退出才能操作。重试先完成原会话的停止/保存/读取租约清理，
   再创建同一媒体的新会话，不仅清除错误或保留旧帧。
5. 内嵌原先只向视频控制层发送错误；现在向媒体库补发阶段/错误转换的最小消息。
   不复制逐帧时钟和音轨列表，不新增媒体库 30 Hz 状态流。会话和修订过滤保持。
6. 失败卸载后，快进快退不会把错误状态清成伪 ready，必须明确重新打开。

事件字段参考 [MPV 事件协议](https://mpv.io/manual/stable/#list-of-events)，
输出属性参考 [MPV current-ao](https://mpv.io/manual/stable/#command-interface-current-ao)。
诊断记录只用于说明已捕获的故障，不用于推断未观察到的设备/驱动原因。

### 真实 Electron 故障与恢复

`npm run test:electron:mpv:audio` 为新增手动运行入口；要求本地已准备 MPV。

实际结果：`build/native-audio-recovery-ROt1hr/acceptance.json`。通过真实媒体库 UI
打开生成的只读 H.264 视频，实际 MPV 进程运行，并注入结构化 AO 失败事件。
两种模式均覆盖加载失败后的重新播放、已附着后失败的显式重试、视频叠层重试
图标、最后读取租约清理、进度时钟继续、原文件哈希与修改时间不变及正常退出。

样本故意是 video-only，故障事件是合成注入，以便不要求测试机有实体声音设备。
它验证的是状态分类与真正的新进程恢复，不证明实体 WASAPI 故障已经修复，
也不代替听音或音频保真验收。没有向生产参数加入 `ao=null` 等静音回退。

最终构建的其他真实应用流：

- `build/native-independent-GRvtnl/acceptance.json`：独立窗口完整回归通过，包括
  暂停准确定位、快进快退、原分辨率截图、全屏、片尾连播、保存失败恢复与退出。
- `build/native-app-flow-JE2Yjy/acceptance.json`：实际内嵌入口准确跳播、暂停末尾、
  时钟继续、连播及源文件哈希不变通过。

独立截图回归补强为等待目标定位确认再截图，而不是只看到 time-pos 更新就发送 C。
生产截图守卫仍拒绝正在定位的画面；没有为通过测试而移除 guard 或生成旧帧。

### 同一最终构建的真实 4K 未通过项

`build/native-presentation-performance-phfQkt/failure.json` 在 ID 196 首次打开
再次得到结构化 `audio output initialization failed`。firstFrameMs 约 496 ms，
但 `readyMs=null`，错误前协议阶段始终为 starting；主页面与叠层均显示音频输出
失败。sourceLoads=1，未静音回退、转码或重载来制造通过结果。测试在此失败，
未继续执行第二样本/后续定位，不能宣称本构建的 4K 对照全部通过或性能已提升。
该实测验证分类/就绪守卫，但选中音轨的实体输出成功路径仍需实机听音验收。
