## 文件与码流检查

31:00–40:00 视频包时间戳检查得到 16,184 个包；排序后的 PTS 间隔中位
约 33.367 ms，最大约 33.434 ms，没有超过 50 ms 的间隔、重复 PTS 或非递增
DTS。正确区分 B 帧重排，不能把包顺序中的 PTS 回退判作异常。

FFprobe 报 `wrong sample count`，并遇到 `missing picture in access unit`。
进一步让本地 FFmpeg 软件解码整个九分钟区间到空输出，日志为
`build/real-segment-rkenlG/ffmpeg-software-decode.txt`：

- 多处 CABAC/宏块解码错误、无效参考帧、`corrupt decoded frame`。
- 一处 `Error submitting packet to decoder: Invalid data found when processing input`。
- 输出 16,182 个解码帧，约 108× 实时速度完成；没有视频文件输出。

这些是实际码流/解码异常证据，超过了单一封装警告。但 FFmpeg 的容错输出和
`drop_frames=0` 是空输出处理中的统计，绝不等于真实 Electron 零丢帧或无坏帧；
约 108× 也不能代表带同步和呈现的 Electron 软件播放效果。
目前没有将错误逐个映射到硬解丢帧时刻，不能认定全部 28.5% 都由坏帧造成。

## 保留失败与限制

- 隔离进程禁用加速解码的 60 秒控制失败：过程中原文件源变成 blob 封装源，
  出现加载、跳转与等待事件，原帧计数重置。稳定源断言正确报错。
  `build/real-segment-xzImGm/segment.json` 保留 `completed=false`；负帧增量、
  零丢帧不参与流畅度比较。未确认该过程中的具体解码错误码，不能推荐全局
  关闭硬件解码。
- 基线之后调用的 8 秒诊断导出期间出现暂停，未取得解码器名和有效帧增量。
  不把其中零计数当作通过；实际 D3D11 解码器身份来自加载前附加的短对照。
- 本机 GPU 信息显示活跃 RTX 4090；GPU 功能启用不等于测到硬解利用率，
  进程 CPU 统计也不等于 GPU 引擎利用率。没有远端电脑同区间数据。
- rVFC 是浏览器呈现回调，不是物理显示器扫描输出；静音测试不验收口型同步。
- 没有用本轮数据证明与用户先前另一台电脑、另一份 5 GiB 视频属于同一根因。

### 已确认的直接诱因

为 `source-segment-timing.py` 增加 `--decoded-frames`，检查**实际解码输出顺序**。
31:00–40:00 的 16,183 个 FFmpeg 输出帧中，原始 PTS 出现 8,006 次回退，
而 `best_effort_timestamp` 的回退与重复均为 0。例如原始帧时间从
1860.325733 回到 1860.125533 秒，回退 200.2 ms。

这和合法 B 帧的“压缩包解码顺序与显示顺序不同”不是同一项检查；此处已经经过
解码，并保留解码器输出顺序。上一轮对包 PTS 排序后的连续性，只能说明时间值
集合没有大空洞，不能证明时间与图像的关联正确。报告位于基线目录的
`decoded-order-timing.json`，源 size/mtime 核对一致。

加载前附加媒体诊断的正常硬解对照，明确捕获到：

- 实际解码器仍为 `D3D11VideoDecoder`。
- `Decoded frame with timestamp 1860.23 s is out of order.`
- 时间为 1860.26 秒的帧早于已显示的 1860.29 秒，因此被实际丢弃。
- 新构建 20 秒原文件观察为 157/607 丢帧，无等待或源替换；不是非 MPV
  路径的性能修复，也不把它与旧构建的小幅波动当成优化。

独立的软件解码对照则确认使用 `FFmpegVideoDecoder`，同样记录时间回退和丢弃，
并在约 1873.539 秒出现 `PIPELINE_ERROR_DECODE`。随后应用尝试原有无损封装
恢复，仍解码失败、帧计数重置，该组保持 `completed=false`。这次补齐了错误原因，
不再将其仅描述为“软件模式可能失败”；也不推荐全局禁用硬解。

两份 JSON 已归集到基线目录的 `hardware-timestamp-evidence.json` 和
`software-decode-failure.json`。结合前一轮码流错误和无损封装对照，已经有明确
证据支持**该样本的码流/时间关联与 Chromium 呈现时序不兼容**，而不是只有
“电脑性能不足”的猜测。尚未将全部丢帧逐个归因，也未定位生成该异常的原始
编码/封装工具，不能泛化到所有大 MP4 或另一台电脑的另一份文件。

### 实施的恢复方式

没有给全部视频切换解码器、增加全片缓存或默认转码。新增受运行库可用性控制的
手动入口：

- 现有播放器展开“播放信息”，点击“使用 MPV 原画播放”；播放失败时也提供
  “改用 MPV 原画播放”。沿用设置中的 MPV 窗口模式，本轮实际桌面验收为独立窗口。
- 从当前绝对位置继续，仅本次视频生效；下一视频仍使用用户默认引擎。
- 切换前保护未保存媒体编辑、保存进度、轨道记忆及音量/倍速等全局设置，
  退出当前全屏/画中画/纯净模式。全局设置保存屏障也应用于原生返回现有播放器。
  保存失败则留在现有播放器；不自动静音、降分辨率、重编码或忽略失败。
- 原生窗口正常停止并保存后，可切回现有播放器。显式交接位置优先于起播偏好，
  修复“用户设置从头播放时，切换引擎意外从头开始”的问题；全局起播设置不改动。
- 原生返回增加重入保护；默认播放链路、原始解码/封装策略、转换权限均保持原样。
