# 第三批：长期稳定性与可诊断

本轮修改源码、构建网页与 Electron 壳并补回归，不生成便携 EXE、不修改真实媒体库、不改写源视频、不集成 MPV；真实 MKV/TS 跳播深度调优仍按用户要求暂缓。

## 已实施

### 1. 长片缓存与生成节流

旧策略会生成整个影片，在缓存超过 2GB 时停止 FFmpeg 并让播放器报错。本轮改为按播放进度维持前向约 90 秒、后向最多 60 秒的目标窗口；达到 1.5GB 容量目标时停止继续向前生成，先收缩旧分片保留区（至约 10 秒）并等待播放消耗。暂停时窗口不向前推进，生产者逐渐停下来，恢复播放后继续同一个 FFmpeg 进程，不重开编码器。

FFmpeg 的 HLS 清单经本地有限管道交给缓存控制器，控制器停止读取会让后续清单写入产生反压；不是挂起 Windows 进程，也不依赖没有可靠边界的进度报告。[FFmpeg 管道说明](https://ffmpeg.org/ffmpeg-protocols.html#pipe)、[HLS 输出说明](https://ffmpeg.org/ffmpeg-formats.html#hls-2)。测试中曾尝试按 progress 控制，但实际分片仍持续增长，故废弃该实现并验证实际文件增长停止。

HTTP 清单使用原子、一致的有效快照，回收前缀后更新 media sequence 与 discontinuity sequence，去掉不再满足追加规则的 EVENT 类型。分片在管理器锁内先打开再流式读取，防止回收与 HTTP 后打开文件发生竞态；Windows 暂时被占用的旧文件会重试回收。

单任务 1.5GB 是节流目标，预留原 2GB 预算的 25% 给编码器、有限管道及在途 GOP；不是严格 2GB 配额。异常长 GOP、单个超大分片或磁盘剩余空间不足仍需要真实样本验证。HLS 内存缓冲仍保持前向 30 秒、最多 90 秒和后向 30 秒。重封装仍复制视频编码，转码分辨率、CRF 18、medium、色彩映射及用户选定档位没有改变。

前端每 5 秒报告原片时间，掌握缓存起点。已回收区间的回看重新生成流；意外遇到 HTTP 410 时保留时间、画质、音轨、暂停状态，同模式自动恢复一次，而非把缓存失效当成编码不兼容并升级为有损转码。持续 410 显示可重试错误，不无限循环。

### 2. 超时、取消与异常恢复

- 查询默认 15 秒、写入 20 秒、字幕 35 秒、备份/恢复及创建播放任务 120 秒；原生目录选择等待用户，不套普通查询的短超时。
- 期限覆盖响应头和正文读取，保留页面主动取消；结束时清除计时器、监听器。查询提供重试，写入超时提示“操作可能已提交”，不自动重放可能改变数据的操作。
- 播放心跳不并发堆积，单次请求 4 秒上限，连续三次失败才进入错误状态，短暂失败不会立刻销毁有缓冲的播放。
- 创建任务采用客户端已知的随机 token。切片/离开取消请求并提交该任务的退役操作；后端保存有时效、有数量上限的取消记录，拒绝晚到的创建，避免响应丢失后留下未知 FFmpeg 进程。
- 启动只回收带有本应用 owner 标记且确认进程已经退出的任务目录；保留未知标记、存活进程、非任务目录和指向缓存外部的链接。Windows 只查询进程状态，不向无关进程发送终止信号。PID 被复用时宁可保留缓存，后续需要更强的实例标识再处理。
- 创建缓存不可写、磁盘写满、FFmpeg 错误日志持续大量增长有明确提示，不让错误日志占满预算后永久“节流等待”。

上轮退出修复继续保留：保存/放弃确认后先释放窗口，媒体服务限时结束，必要时只终止本次服务进程树。主动放弃、系统强杀或断电不保证保存最后一瞬间的数据。

### 3. 版本、数据路径和日志

构建自动写入版本、API 协议 2、源码摘要构建 ID 与构建时间，网页内置相同标识，服务启动时捕获自己的标识。开发服务同时核对当前源码；旧服务不会通过读取磁盘新文件冒充新构建。启动先握手再载入设置；不匹配时说明两端编号并提供重新启动和诊断入口。

“媒体库设置 → 运行诊断”默认折叠，按需查询：启动方式、实际数据目录及数据库、两端构建、运行时间、Python、FFmpeg/FFprobe、任务数、缓存目标/使用量、节流任务及待清理目录。刷新/导出可重试，关闭设置取消未完成查询。诊断不联网，导出文件包含本地路径，分享前需检查。

桌面启动和后端日志各自保留当前文件及两份历史，每文件最多 4MB；超大消息截取最近内容，不因不可写日志导致播放或退出崩溃。只轮转 app-owned 的两个固定日志名，不遍历或清理用户数据目录。单任务 FFmpeg 日志超过 4MB 的持续错误视为异常，停止任务并提示，而非继续扩张。

打包脚本已加入构建元数据资源，但本轮不执行打包。现有版本号仍为 0.2.0，使用构建 ID 区分源码状态，不把旧 EXE 当作新版验收结果。
