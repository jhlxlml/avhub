# M4：新目标抢占、20 次跳播与资源证据

2026-10-27。本批继续开发态单屏 SDR 范围。应用构建 `4d17ca0c42e495f4`，原生宿主 SHA-256 `97154ee3d2ad5fb8ccf0b95bc22e70d80c205ed9e3f1575656be10aeab2250d8`；libmpv DLL 校验和未改变。版本仍为 0.2.16。

## 根据实测修改

1. 无损索引封装：新目标不在浏览器缓冲中时，通过现有 HLS 实例的 `startLoad(position, true)` 终止旧分片加载和错误退避，直接加载新目标。保留 MediaSource、既有缓冲、原播放会话及暂停/播放意图；目标已缓冲时不重启加载。只用于 indexed-remux，不改变 direct 或 indexed-ts。后端继续按现有 seek revision 取消过期窗口，无视频或音频转码。
2. 原生暂停跳播：旧宿主的固定 100 ms 接受范围可能把 7.92 秒请求的 8.00 秒画面算作成功。现在已知有效帧率时按一帧加 2 ms 核对暂停落点，上限仍为 100 ms；播放中的时钟容差保持原策略。实际越过目标才执行既有的最多两次纠偏，最终仍需真实 GPU 交接确认。
3. 原生资源诊断：私有宿主协议增加只读 resources 请求，采集本进程 CPU、私有内存、工作集、句柄、DXGI 内存预算及进程 I/O；未向 renderer 暴露任意命令接口。进程 I/O 包含缓存命中及协议管道，不能当作物理硬盘吞吐。未采集 GPU 引擎利用率。

## 同源容器对照

源素材、三个容器和帧码方法沿用第 21 批，每链路增加到 20 个固定非单调目标。每个目标以解码画面帧码核对；新旧测试的生成源 SHA-256 相同。首次打开及 OS 文件缓存没有人为清空，不宣称冷盘对照。

修改前 `build/m4-seek-matrix-qLjvRQ/report.json`：Chromium 三条链路和 MPV MP4 完成各 20 次；MPV TS 在第 16 个目标 7.92 秒失败，保留为失败报告，不能作为完整六链路基线。其 Chromium indexed-remux p50/p95 为 31.3/1102.1 ms。三个慢目标均在约 13–20 ms 的旧分片 503 后等待约一秒，随后新分片生成只需约 30–40 ms；缓存窗口统计为 10 次生成、3 次取消、0 次生成失败。

修改后第一次 `m4-seek-matrix-VHPoc2` 六链路全部通过；其中 indexed-remux p95 64.1 ms。该轮开始期间另运行了轻量单元测试，故另做全串行复测，避免仅据这轮判断性能。

最终串行 `build/m4-seek-matrix-ptuxto/report.json`，单位 ms：

| 实际链路 | p50 | p95 |
| --- | ---: | ---: |
| Chromium MP4 direct | 29.45 | 32.10 |
| Chromium indexed-ts | 29.25 | 30.30 |
| Chromium MKV 强制 indexed-remux | 29.85 | 60.80 |
| MPV MP4 原文件 | 20.00 | 34.40 |
| MPV TS 原文件 | 236.80 | 253.10 |
| MPV MKV 原文件 | 19.90 | 32.70 |

20 个样本的 p95 使用最近秩第 19 个值，报告另保留最大值及全部目标；不能与第 21 批十样本的最大值直接等同。所有目标画面通过；Chromium 每次打开只创建一个播放源，原生 sourceLoads=1。封装尾延迟的收益来自目标分片及时获得调度，并非隐藏缓冲状态。实际的旧分片 503 仍被记录；未通过缩短所有错误重试来掩盖服务故障。

TS 原生仍明显慢于该短样本的 indexed-ts；没有依据把它自动强制交给 MPV，默认引擎策略保持不变。

## 稳定性与失败记录

`build/render-app-soak-fPlucn/report.json` 使用上一个仅增加资源采样的宿主，连续播放 900.18 秒，像素/墙钟比 0.999985，解码及显示丢帧增量均为 0；22520 次 GPU 交接均完成释放，退出后源保护和宿主已释放。但验收 FAIL：活动阶段句柄范围 795–814（范围 19）及显存回收范围超过先设活动范围阈值。该结果没有改写为 PASS，也不覆盖随后修改的最终宿主。

本批补充 M2 已使用的 `resource-convergence.cjs`：播放前后各 15 次暂停且 GPU 读者已释放的采样，区分驱动回收带来的下降范围与相对基线的向上增长。仍保留原始活动范围和是否超限的结果；增长预算沿用 M2 的私有内存/显存 64 MiB、句柄峰值增长 16、稳定后增长和空闲范围各 8。

最终宿主 `build/render-app-soak-u6tQrh/report.json` 再次完整播放 900.18 秒，像素/墙钟比 0.999974，解码与显示丢帧增量均为 0，22526 次 GPU 交接均完成释放；宿主与源保护在退出后释放。严格验收仍 FAIL：句柄暂停基线中位数 797、活动峰值 814，向上增长 17 超出预算 16。暂停后中位数 799（增长 2），15 次空闲采样范围 0；原生私有内存峰值增长 14.15 MiB，显存峰值向上增长 0，Electron 后段私有内存范围 65.9 MiB。没有提高阈值或把该报告标记通过；完整资源门槛尚未放行。

`build/render-handle-attribution-0B1IV8/report.json` 在相同宿主上额外施加 12000 次顺序状态请求，原生句柄未增长，未复现六分钟附近峰值。该诊断不是播放性能基准，也不足以排除其他类型的瞬时增长。测试工具只针对已核对路径的专属宿主查询句柄类型，临时复制的查询句柄均关闭，不读取对象名称。

`build/render-handle-attribution-Fbuu5d/report.json` 是同一未改动宿主的 420.64 秒正常播放稀疏类型跟踪，不额外施加查询压力。句柄基线 797、峰值 812、短暂停后 807；不能把该轮短暂停残留 10 解释为满足空闲增长 8 的门槛。峰值时类型变化：Event +6、Semaphore +6、Timer +6、IoCompletion +2、ALPC Port -4、Token -1，净增 15。File 始终 45、Section 29、Thread 66、DxgkSharedResource 1；另有 159 个固定的 type-56 对象无法查询类型名，报告保留未知状态。

这些证据把后续排查范围缩小到运行时/驱动的计时和同步对象生命周期，但没有定位创建模块或证明不存在泄漏。下一步应对这些类型做较长空闲衰减与创建模块归因，依据结果修复真实未释放资源；不强制 GC，不靠扩大门槛放行。严格资源验收仍未通过，M4 不整体放行。
