## 修正实际统计问题

本地固定 MPV 源码 `build/mkv-index-candidate-ov5n3y7s/source/video/out/vo.c` 的 `forget_frames()` 会清零 drop_count；`player/command.c` 的 frame-drop-count 属性读取该值。因此跳播后的末次读数不是整个播放会话累计值。

108 的原始 20 分钟报告保持不变。另存 `build/iteration-109-drop-retrospective.json`：106 个有序采样中有 16 次计数下降，末次值 39，能够确认的输出增量下界为 **524**，而不是累计 39；真正总数仍可能更高。第一读数作为基线，不推测丢失区间，也不把计数归零当作负丢帧。修正了 108 文档及对话表述，不改写原始证据。

改动：

- 测试共用 `summarizeFrameCounter`，输出 first/last、观测增量下界、计数下降、seek 边界和缺失样本；固定 `totalIsExact:false`。
- 并发 soak 新增每次采样的实际 seekId，避免只凭数值下降识别重置；cadence 报告也使用统一口径。
- 独立 MPV 诊断增加 `dropCounterScope:current-mpv-reading-may-reset-on-seek`。内嵌诊断原先没有导出丢帧字段，现在补上真实 dropped/decoderDropped 及同样的范围标记。
- 控制区高级诊断给“显示丢帧”补充当前读数/可能重置的说明，不隐藏计数、不修改等待提示或播放错误。

## 10ms / 6ms 实验与回退

使用原只读 4K60 VP9 MKV（索引 1240）、相同三个策略/目标位置，每段持续 15 秒，在真实可见 Electron 中记录实际 GPU 完成、原生管线、轮询次数、主进程和宿主 CPU。硬解 d3d11va、色彩/分辨率、队列和 GPU 确认条件均不改。

| 模式/目标 | 10ms GPU 间隔 P95 / max ms | 6ms GPU 间隔 P95 / max ms | frame 请求数 10ms → 6ms |
| --- | --- | --- | --- |
| 快速 / 1040s | 22.38 / 35.01 | 20.82 / 38.20 | 1421 → 2186 |
| 精确 / 1040s | 21.74 / 41.88 | 21.55 / 44.62 | 1299 → 1850 |
| 快速 / 218s | 21.91 / 32.10 | 21.21 / 43.86 | 1335 → 1988 |

证据：`render-frame-cadence-gqpLTJ`（10ms）、`render-frame-cadence-XrT5z8`（6ms），均 PASS/0、原文件哈希不变，源加载一次。两组短时播放均未复现之前长测的计数增长；主进程/宿主 CPU 变化不一致，且未测全系统功耗。未控制 OS/驱动缓存，也不是统计充分的因果实验。

6ms 的 P95 收益小，最大间隔没有改善，frame 轮询增加约 42–54%，证据不足以采用。**已恢复原 10ms 节奏及注释**；没有提交、启用或包装成有效优化，不以调低轮询掩盖真实丢帧。实际生产改动只保留诊断口径修复，108 的快速缺省修复继续保留。
