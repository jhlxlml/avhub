# M4：同源跳播与超时恢复

本批继续开发态单屏 SDR 原生嵌入，未开启默认引擎或发行能力。构建 `92b970ddf212fd33`；实际原生宿主 SHA-256 为 `ee4c164623017f1c4dd28c55e594fc6a00c392b5779a02093d0b8d98a72dc086`。原生宿主哈希独立记录，因为应用构建标识不覆盖其 C# 源码。

## 实际问题与修复

生成的 H.264 TS 在真实 Electron 中请求 1.72 秒时，MPV 曾落在 2.00 秒，像素帧码为 50 而不是目标 43，目标帧确认超时；MP4 同目标能完成。`build/m4-seek-matrix-gLcjCa/report.json` 保留了复现现场。新宿主仅在观察到完成跳播后实际越过目标时，临时调整 demuxer seek preroll，最多重试两次。暂停纠偏期间保留用户最新播放意图；目标帧经过 GPU 交接确认后再按意图恢复。新请求拥有独立编号，不允许旧帧完成新请求。

若一直收不到目标帧，前端在超时后报告失败，并以会话和请求编号取消该次定位。宿主清除本次纠偏状态；主进程在确认取消后恢复用户的播放意图，不把超时记为目标帧成功。故障时保留可恢复错误。该路径不改变源文件、编码、分辨率、位深或色彩。

## 测量

`build/m4-seek-matrix-fjn2vq/report.json` 使用一段 640×360、25 fps、无音频的生成视频，将重复的六秒画面以流复制封装为连续 24 秒的 MP4、TS 和 MKV；流复制时调整了 H.264 色彩元数据以满足测试显示条件，没有重新编码。Chromium MKV 的索引封装由测试明确强制，并不代表默认选择。三个容器各自测量十次暂停跳播，另验证一次播放中跳播；所有目标以真实解码画面像素帧码确认。源文件哈希、大小及修改时间前后不变。

| 链路 | 暂停跳播中位数 | 十次样本的第 95 百分位 |
| --- | ---: | ---: |
| Chromium MP4 直放 | 30.9 ms | 106.8 ms |
| Chromium TS 索引流 | 30.8 ms | 95.5 ms |
| Chromium MKV 强制索引封装 | 31.4 ms | 1110.2 ms |
| MPV MP4 原文件 | 18.9 ms | 38.6 ms |
| MPV TS 原文件 | 235.2 ms | 254.0 ms |
| MPV MKV 原文件 | 20.1 ms | 35.9 ms |

样本量只有十次，百分位等于其中最慢的一次；结果仅用于该机器和短合成样本，不代表实体屏幕扫描输出、冷盘读取或真实长视频体验。索引封装尾延迟需进一步分解服务端与 I/O，不能据此直接断定瓶颈。测试未读取或修改 `E:\downloads`。

`build/m4-native-seek-intent-qgJ03S/report.json` 是真实 TS 和实际画面，在 GPU 已交接后人为延迟确认，用于验证播放/暂停意图、新目标抢占和 15 秒超时恢复；它不是性能测量。`render-app-faults-QrUqto` 与 `render-app-startup-intent-9aPrhZ` 实际 Electron 回归通过；播放适配器单元测试 22 项通过。

4K SDR10 真实 Electron 回归 `build/render-app-flow-yAn1DK/report.json` 通过目标像素、16 位 PNG 截图和窗口操作。此前 `render-app-flow-poVViG` 在全屏切换后未能点击隐藏控制栏，测试的鼠标唤出动作在窗口变化后可能没有产生移动；补充实际鼠标移动和控制栏可见断言后重跑通过。该单次重跑不能证明所有窗口环境均无问题，失败现场继续保留。
