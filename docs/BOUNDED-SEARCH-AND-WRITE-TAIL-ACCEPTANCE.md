## 有界匹配 ID 查询

全库文本搜索之前需要先 COUNT，再为分页重新求值 LIKE。此次将优化从零/单条
扩展到 **最多 1024 条匹配**：

1. 同一只读事务内，按明确的 id ASC 顺序查询最多 1024 个匹配 ID。
2. 少于上限即得到精确总数；达到上限则只 COUNT `id > 最后一个 ID` 的剩余部分，
   不重扫已经处理的前缀。没有按数量或耗时估算总数。
3. 总数不超过上限时，按 ID 主键取得当前页并执行原有排序，无需再运行 LIKE。
4. 超过上限则丢弃 ID 集合，沿用原来按排序索引分页的路径。

采集、续计数、分页始终处于一个 WAL 快照中，不跨请求缓存，避免标题/收藏/
missing 等并发变化导致漏项或泄漏旧筛选结果。ID 集合至多 1024 个，SQL 参数
也有界，不会把十万或百万匹配 ID 全部传给 Python、构造巨型 IN 或持久化新索引。

仅作用于原本就物理扫描的全库搜索；目录、收藏、影片类型、分辨率等组合筛选
继续使用原计数/索引路径，未改变无搜索列表和旧非分页接口。Unicode、大小写、
`%` / `_` / 反斜杠的字面搜索、分页钳制、排序规则和精确计数均保留。

NOT INDEXED 不阻止 rowid 定位，见 [SQLite 官方说明](https://sqlite.org/lang_indexedby.html)。
测试和基准计划核对了首段扫描、剩余部分主键范围计数、IN 主键定位及原索引分页，
不依赖没有 ORDER BY 时碰巧返回的顺序。

## 后台写入长尾：仍然存在

两轮顺序独立运行，完整证据分别为
`build/bulk-playback-avhub-bulk-playback-M2ZVK9/acceptance.json` 和
`build/bulk-playback-avhub-bulk-playback-ex30Um/acceptance.json`。

| 轮次 | 首次元数据扫描 | 扫描中暂停保存 | 扫描中返回 | 增量扫描 / 更新 | 最大 commit |
| --- | ---: | --- | ---: | --- | ---: |
| M2ZVK9 | 26572 ms | 20 / 21 / 23 / 30 ms | 130 ms | 229 ms / 0 | 128.351 ms |
| ex30Um | 26871 ms | 30 / 24 / 23 / 30 ms | 132 ms | 227 ms / 0 | 189.222 ms |

暂停保存是包含 Electron/HTTP/本地提交的墙钟，最大 commit 来自全程 bounded
诊断的 lifetime.serialized.max_ms，并不是仅从快速保存里挑选。两轮包含封面排空
的首次墙钟为 86972 / 86926 ms，不能把约 27 秒元数据完成称为全部封面完成。
增量阶段保存为 35/20、38/25 ms，返回 148 / 150 ms。

- 两轮 completed/cleanExit/sourceUnchanged=true、errors 为空、封面排空成功。
  每个成功保存响应都与实际 committed 诊断 ID 及落库进度核对。
- 首次播放段各增加 251 个真实解码帧，增量段各 21 帧；开始观测后 waiting、
  stalled、源重载和掉帧均为零。扫描中 4 次搜索，每阶段完成后还核对两个末页。
- 真实桌面为 175% DPI、32 Hz，保持正常 GPU 策略、sandbox 与后台节流；附加
  Playwright 不等于用户无观测器环境，也不等同物理屏幕出帧率验收。
- 首轮保存仍能观测到约 2.7 ms 的实际写锁等待，后台操作最长等待约 116.5 ms；
  第二轮后台最大等待约 188.9 ms。保存优先只能调整排队，不能抢占已经开始的提交。
- 此次未改变写事务、FULL、默认自动检查点或串行保存优先门。没有证据表明
  搜索优化消除了 fsync/检查点等长尾；仅凭这些计时也不能把每个长提交都归因于
  某一种底层 I/O。两轮约三分钟的生成负载不是数小时长期稳定性结论。

下一步建议先扩充持续桌面使用中的保存/慢提交关联样本，区分 SQL 事务体、锁
等待与 commit I/O，再决定是否调整后台提交批次；不应直接改 NORMAL/异步确认。
超过 1024 条匹配、特别是深 OFFSET，仍是未提速范围；暂不默认增加全文索引，
避免为用户常用的较小媒体库增加扫描、容量和写入负担。
