# 保存优先排队与 SQLite 升级评估

后续的私有运行库接入与验收见 [项目私有 SQLite 运行库接入](PRIVATE-SQLITE-RUNTIME-ACCEPTANCE.md)。
以下保留评估时仍使用旧引擎的原始测量，不用新结果覆盖历史长尾。

本地桌面迭代，应用版本不变；不打包、不发布、不改系统 Python 或 SQLite DLL。
延续 [保存长尾关联验收](WINDOW-CALIBRATION-AND-SAVE-TRACE-ACCEPTANCE.md)。
所有新写入测试仅使用自动生成的隔离数据库和视频，不操作用户的媒体目录。

## 1. 实现范围：优先排队，不抢占提交

`SavePriorityLock` 替换原串行写入 RLock，保留跨线程互斥与同线程可重入：

- `progress-save` 请求排在已经等待的普通数据库操作前；普通队列及保存队列
  各自保持 FIFO。有普通操作等待时，最多连续服务 4 次保存，再放行一次普通
  操作，避免扫描、封面发布和维护工作长期饿死。
- 正在执行的 SQL、提交、恢复及持有外层锁的维护操作不可抢占。因此该调度
  能减少排队叠加，**不能消除当前事务自身的长提交**，也不是系统线程实时优先级。
- 原同步级别、每连接提交、默认 1000 页自动检查点、恢复独占边界不变。
  成功响应仍在实际提交后返回，不缓存成功、不提前确认、不丢弃进度。
- 超时/异常会移除排队票据；重入不会重复排队。原来的嵌套恢复/备份锁继续
  工作，不能因为换了队列就绕开文件操作、读写门或恢复校验。
- `/api/diagnostics` 增加 `database_write_queue`：有界标量计数与当前等待数，
  不记录文件名、路径、SQL 或任意客户端标签。`served_*` 是取得队列的次数，
  不代表实际写事务、fsync 次数或物理 I/O。

定向回归覆盖优先顺序、两队列 FIFO、连续保存上限、重入、超时清理和错误线程
释放；实际 SQLite 并发测试要求后台元数据写入读到前面保存的进度，且成功响应
携带对应已提交标识。另保留“已经执行的扫描事务必须等待”与提交失败不报成功
测试，不能通过忽略这些约束让延迟数字变小。

## 2. 检查点隔离实验：不能把慢提交一概归给 checkpoint

脚本 `scripts/benchmark-sqlite-checkpoints.py` 使用临时数据库，每轮 1000 次模拟
元数据写入、三个索引、间歇进度更新；各次提交均核对 `synchronous=FULL`。
按默认 / 分离 / 分离 / 默认顺序运行，证据：
`build/sqlite-checkpoint-1792502587047261600/report.json`，SQLite 3.50.4。

| 轮次 | 提交中位数 | 提交 P95 | 提交最大值 | 显式 PASSIVE 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 默认 0 | 1.896 ms | 2.134 ms | 11.747 ms | 不单独测量 |
| 串行分离 1 | 1.890 ms | 2.137 ms | 60.718 ms | 3.127 ms |
| 串行分离 2 | 1.892 ms | 2.138 ms | 156.681 ms | 4.740 ms |
| 默认 3 | 1.890 ms | 2.143 ms | 502.638 ms | 不单独测量 |

分离轮只在自己的临时库禁用自动检查点，按基线 WAL 复用前的位置执行串行
PASSIVE；生产代码没有禁用自动检查点，也没有加入并行检查点线程。每轮最终
完整性、行数与进度均核对通过；观测 WAL 最大约 4.13 MB。

WAL 头部 generation 改变只说明复用，不是直接测得内部自动检查点时长。不同
轮次受缓存、顺序和系统负载影响，不能相减推出精确 checkpoint 成本。分离轮
最慢提交并不发生在执行显式检查点的那次写入；这支持继续分辨提交/操作系统
调度等因素，**没有证明物理硬盘、杀毒软件或某个系统调用就是根因**。亦不能
据此承诺升级 SQLite 就会消除此前的几百毫秒保存长尾。

## 3. SQLite 升级可行性

### 当前运行库与打包路径

2026-10-21 本机实际探测：

- CPython 3.13.11，64 位；标准库 `sqlite3` 实际加载 SQLite **3.50.4**。
- `sqlite_source_id()`：
  `2025-07-30 19:33:53 4d8adfb30e03f9cf27f800a2c1ba3c48fb4ca1b08b0f5ed59a4d5ecbf45e20a3`。
- Windows CI 配置同样固定 Python 3.13.11；`build-windows.ps1` 使用选定 Python
  执行 PyInstaller，SQLite 来自其原生依赖，不来自 npm/Electron 的数据库引擎。
  本轮没有重新打包，以上不冒称已对所有历史 Release 二进制逐个取证。
- 项目使用标准库连接/事务、只读 URI、行对象、备份 API 和常规索引/SQL；
  没有发现必须迁到另一套驱动才能使用的 SQLite 功能。

Python 的 `sqlite3` 模块版本与底层 SQLite 版本不是一回事；`pip install` 项目
现有依赖、升级 Electron、安装 sqlite3 命令行工具，都不能单独证明后端运行库
已经变更。[Python sqlite3 文档](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.sqlite_version)

### 升级的主要收益是安全修复

SQLite 官方说明：旧版本存在罕见的 WAL-reset 数据竞争，触发条件涉及不同线程
或进程上的多个连接同时写入/检查点；修复在 3.51.3 及后续版本，另有 3.50.7
分支回补。官方认为应升级，但不将其描述为一般用法下的紧急事故。
[官方 WAL 说明](https://sqlite.org/wal.html)、
[3.51.3 发布说明](https://sqlite.org/releaselog/3_51_3.html)、
[3.50.7 回补记录](https://sqlite.org/src/info/c7facf7ac58d2cda)

本项目目前串行化写入和受控检查点，保持这个边界，不额外制造并行 checkpoint。
没有证据表明现有媒体库已触发该问题；普通压力测试通过也不能证明旧引擎已修复。
升级是值得推进的安全维护，而不是修复视频解码或保证跳播提速的替代方案。

### 推荐路径

**可以升级，优先保留标准库 API，在项目私有后端运行时中固定已验证的官方
x64 SQLite，先隔离验证，再同步 CI 和打包入口。** 不替换系统 Python 的 DLL。

截至评估时，官方公开下载页提供 3.54.1 Windows x64 DLL 与 SHA3-256；可作为
隔离验证候选，但尚未验证，不能直接宣称项目支持。3.51.3 是上述主线修复的
最低版本，3.50.7 是最小分支变更备选；后者是回补分支，不应假定存在与主线
相同的官方预编译分发渠道。[SQLite 官方下载页](https://sqlite.org/download.html)

不建议为此直接更换 Python 大版本或引入 APSW/pysqlite3：前者扩大依赖回归面，
后者还要重新验证连接/事务/备份行为与 PyInstaller 收集方式。也不在应用启动时
联网更新或任意寻找系统 DLL。必须控制实际加载路径、来源、架构、哈希及回退。

一个容易遗漏的点：检查到的 CPython `v3.13.16` Windows 构建属性仍引用
`sqlite-3.50.4.0`。因此不能仅把 CI 的 Python 版本号调高就认定修复已生效；
必须探测实际加载版本、source ID 和二进制来源。此为构建配置证据，不等于本轮
已下载并实测该 Python 发行包。
[CPython 官方构建配置](https://raw.githubusercontent.com/python/cpython/v3.13.16/PCbuild/python.props)

### 接入前的验收门槛（尚未实施升级）

1. 候选在项目拥有的隔离目录运行，官方固定 URL/哈希，核对 x64 架构；验证
   `sqlite_version()`、`sqlite_source_id()`、线程模式及项目需要的编译选项。
   验证开发后端实际加载该文件，不仅调用一个独立 SQLite CLI。
2. 保留 FULL、自动检查点和保存确认语义；用 SQLite backup API 创建一致性
   快照，在副本上做旧→新读取/写入、重开、完整性、外键、备份/恢复与回退测试。
   不直接复制运行中的主库丢弃 WAL，也不删除用户 WAL/SHM。
3. 全量后端回归，真实 Electron 的扫描/封面/播放/保存并发、关闭、迁移和恢复；
   同条件测分位数与最差提交、锁等待、源重载、解码帧，而不只比较查询均值。
4. 通过后固定开发、CI 和未来打包的同一运行库及来源清单，并验证将来冻结后端
   确实携带同一引擎；该打包验收需另获用户打包授权。本轮仅评估，不发布。

仅运行库更新通常不要求改变本项目 schema，但查询计划、编译选项、ABI 和
异常行为仍有回归风险，不能省略上述验证。正式切换前保留一致性备份和旧运行
环境；回退也只用核验过的副本流程，不对原库做不可逆的就地试验。

## 4. 真实 Electron 验收

生产源码在完整重建后保持不变，构建 **`f8b399a21ed7a21d`**，仍使用 SQLite
3.50.4。性能两轮单独顺序运行，不同时跑其他回归套件。沿用 1200 个生成视频
与 60 个子目录、真实 FFprobe、扫描期间约 5/30/55/80% 暂停保存、扫描中返回、
封面让步后排空、再做增量扫描的负载。

| 证据后缀 | 首次扫描 | 首次暂停保存 | 扫描中返回 | 增量扫描 / 更新 |
| --- | ---: | --- | ---: | --- |
| `g7D3rw` | 26539 ms | 29 / 19 / 22 / 28 ms | 143 ms | 207 ms / 0 |
| `a6AdHJ` | 26391 ms | 18 / 32 / 31 / 24 ms | 152 ms | 699 ms / 0 |

完整报告分别为：

- `build/bulk-playback-avhub-bulk-playback-g7D3rw/acceptance.json`
- `build/bulk-playback-avhub-bulk-playback-a6AdHJ/acceptance.json`

两轮均 completed / cleanExit / sourceUnchanged 为 true，退出后无 WAL，错误为空，
封面任务无失败且排空。成功保存响应逐次对应已提交数据库操作，并核对暂停
位置与落库进度；增量保存分别 26/23、29/27 ms，返回 151 / 133 ms。

首次播放段各增加 **250 个实际解码帧**，增量段分别 20 / 21 帧；初始准备后
waiting、stalled、播放源重载、掉帧均为零。播放样本/模板核对哈希，1200 副本
核对大小与修改时间，非逐份哈希。全部为自建隔离样本，不修改用户原文件。

队列诊断证明真实保存进入了优先通道：首次阶段结束各 served_saves=7，第一轮
累计发生 1 次有普通操作等待时的保存晋级，第二轮为 0。两轮都不是高争用保存
负载，不能单凭 18–32 ms 就宣布已消除长尾或计算普遍提速比例。确定性的排队
顺序由并发单元/SQLite 集成测试另行证明。

后台提交最大值仍分别 **201.857 / 267.985 ms**，不可抢占的已开始提交没有因
优先队列而消失。增量扫描第二轮也较慢，保留原值，不拿快轮次覆盖。首次阶段
含封面排空墙钟 86822 / 87886 ms，不把约 26 秒元数据完成描述为全部封面完成。

本轮 API 报告窗口 1436×748 DIP、工作区 1463×775、**175% DPI**、32 Hz，正常
GPU/sandbox/backgroundThrottling、附加 CDP。与历史 125% 环境不同，不作严格
同条件 A/B 性能百分比比较；样本仅 320×180、12 fps、SDR H.264、静音，不等同
真实高码率、音频设备、物理显示器或 4K 播放验收。
