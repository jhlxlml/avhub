## 保存：关联真实 HTTP 响应与数据库阶段

- 成功保存增加只读诊断响应头 `X-AVHub-Save-Trace`，JSON 返回字段不变。
  该标识在实际提交、关闭连接后才写到响应；提交失败仍报错，不能假报成功。
- 诊断保留最近 32 次保存，包括快保存。慢操作的既有最近 32 / 最差 8 项仍保留。
  用服务端 scope/connection ID 关联，只有固定标签 `progress-save`、`scan-media`、
  `cover-publish` 或 unlabelled，不记录源路径、标题、SQL、客户端自定义标签。
- 在进入串行队列时记录当时正在执行的写入 ID。等待可能跨越多个写入，所以它
  明确叫“入队时观测的写入”，不是把全部等待归给单个写入的证明。
- 上下文按请求/线程隔离，嵌套与异常退出后恢复；连接失败也清除活动写入状态。
  统计容量固定，不以请求 ID 建立无限增长的字典，不改原数字耗时百分位计算。
- 修正错误计时：如果 `commit()` 本身失败，其耗时仍计在 commit，而不是混进
  SQL 事务体；记录 committed/failed，不把诊断记录当作 HTTP 成功的替代品。
- 不改 FULL 同步级别、自动 checkpoint、写入顺序、确认时机或重试文件操作。

## 真实 Electron 批量导入中的关联样本

继续使用既有 1200 个生成视频 / 60 个子目录的负载：已有视频播放期间首次导入，
约 5/30/55/80% 暂停保存，扫描中返回，封面按播放优先级让步并在返回后排空，
随后增量扫描。采样为 320×180、12 fps、SDR H.264，不是高码率真实文件验收。
正常 GPU/sandbox/backgroundThrottling，Playwright/CDP 附加；性能期间不跑其他套件。
每个成功响应标识均匹配其已提交记录，并核对实际进度。新增诊断 GET 不计入
暂停保存耗时；本轮不与没有这些采样的旧轮次计算速度提升百分比。

第一轮 `build/bulk-playback-avhub-bulk-playback-aQb2F4/acceptance.json`：

- 首次扫描 **27326 ms**；暂停保存 **452 / 24 / 16 / 26 ms**，扫描中返回 139 ms。
  增量扫描 192 ms、更新 0，暂停 29/24 ms、返回 148 ms。
- 452 ms 保存响应 scope 375、连接 376：锁等待 **419.602 ms**，事务体 3.983 ms，
  提交 **2.019 ms**，连接总计 425.855 ms。其余时间包括事件/HTTP 调度及核对读取。
- 入队观测的写入为 scan-media 连接 372、scope 371，提交 **647.300 ms**；
  另一扫描连接 374 在同期间等待 620.398 ms。关联 ID 与时间吻合，足以支持本次
  保存主要在等待后台写入，不能再仅因 AnyIO 线程名接近就猜测是该请求。
- 不能据此认定 419.602 ms 全由单个事务造成，或 647.300 ms 都是物理写盘。
  现有观测没有拆分 SQLite 内部自动 checkpoint、同步调用与操作系统调度。

第二轮 `build/bulk-playback-avhub-bulk-playback-hh1JEj/acceptance.json`：

- 首次扫描 26587 ms，暂停保存 20/18/26/19 ms，扫描中返回 118 ms。增量扫描
  194 ms、更新 0，暂停 25/22 ms、返回 121 ms。未撞上同等保存长尾，但全程
  后台提交最大仍为 167.383 ms，不把该快轮次拿来覆盖首轮慢记录。
- 两轮均 `completed:true`、`cleanExit:true`、`sourceUnchanged:true`、退出后 WAL
  文件不存在、错误为空。两个首次播放段各解码增加 251 帧，两个增量段各增加
  20 帧；初始准备之后 waiting/stalled/播放源重载/掉帧均为零。
- API 报告窗口 1446×788 DIP、工作区 1536×816、125%、32 Hz；不是物理刷新率
  或高帧率验收。分别 87314 / 86814 ms 的首次阶段墙钟包含封面排空；约 27 秒
  是元数据扫描完成，不能称全部封面生成完成。全部源为隔离生成样本。
- 暂停/返回的成功响应均匹配实际 committed 连接记录；播放样本、模板核对哈希，
  1200 份副本核对大小/mtime，非对每份副本逐一计算内容哈希。源文件未修改。
- 每轮首次串行连接操作增量 4864 / 4872、只读 8593 / 8596；这是应用连接操作，
  不是写事务、fsync 或物理 I/O 次数。没有改变上一轮移出纯读竞争的结构。

当前完成的是窗口修复和长尾的可关联定位，**不是保存尾延迟已根治**。下一步
应在保持 FULL 与真实提交确认的前提下，补齐提交/检查点阶段证据，评估后台
扫描写入与用户保存的调度；不能对已开始的长提交承诺可以立即抢占或消除等待。
