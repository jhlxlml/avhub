# MPV 正式化目标与首轮验收

## 产品目标

将 MPV 从源码试用收敛为可随桌面包交付、故障可恢复、行为可解释的原画播放引擎。
推荐原生独立窗口，内嵌保留；不强制替换已有默认引擎，不以删除“试用”字样代替验收。
原文件只读、无自动转码或位深/色彩转换、源占用保护与保存失败屏障继续适用。

## 本轮完成

1. **统一可用性门槛。** `nativeRuntime.ts` 离线验证固定 EXE 与 `LICENSE.GPL` 的
   SHA-256；普通文件/大小/真实路径与校验期间变更均有检查。检测不执行程序、不下载。
   每次打开检查文件身份；未变化结果复用，多个相同请求合并，最多一个摘要校验在途。
   失败原因区分缺失、无效和不支持平台，不把分发许可门槛与运行库可用性混为一谈。
2. **两种模式共用启动检查。** 修复独立窗口绕过内嵌运行库检查的问题；在申请视频读取
   租约、创建播放器之前拦住失败，不自动切引擎或转码。已开启会话的关闭不依赖运行库
   检测成功；即使用户改动运行库，退出及保存路径仍保留。
3. **原位重试。** 页面跟踪两种模式的有效最新时间，重试时再取当前会话快照，随后完成
   原会话保存与退出，再从该时间打开同一源；解码器已退出时保留最后观测位置。
   起播故障仍从原始选择位置重试，未保存记录不会被静默跳过。
4. **设置体验。** 提供显式“重新检测”，检测期间禁止启用；不需要关闭重开设置。
   首次设置启用 MPV 且无窗口偏好时，原子保存独立窗口选择；旧 MPV 的缺省内嵌行为
   以及任何显式窗口选择均保留。说明按模式显示，复杂快捷操作归入既有帮助。
5. **交付准备。** Electron 文件清单纳入只读运行库 manifest，确保未来打包后同样可验证。
   本轮没有把未完成分发准备的 EXE 偷偷加入包，没有打包、发布或升级版本。

## 验收口径

- `native-runtime.test.mjs`：三项通过，覆盖并发合并/缓存、EXE 内容变化、许可缺失、
  无效清单、不支持平台和非普通 EXE 文件；模拟文件不是实际解码验收。
- `native-launch-lifecycle.spec.ts`：15 项 renderer harness 通过，其中新增两种模式重试时
  优先取最新快照位置；旧会话隔离、保存失败、引擎切换、退出恢复仍通过。
- `native-runtime-settings.spec.ts`：重新检测、启用禁用、首次推荐窗口与旧选择保留。
  与上述生命周期 harness 合计 16 项在最终构建通过。
- `native-engine.mjs`：真实 Electron + MPV，生成 30 秒 H.264 / SDR / 8-bit 640×360 视频。
  实际设置启用与 SQLite 偏好验证、两种模式故障注入、重试后的真实解码时间、正常关闭、
  源 SHA-256 检查。运行库故障/解码器故障为明确注入，不称为硬件故障复现。
- `native-independent.mjs`：完整独立窗口操作回归，覆盖跳播、全屏、截图、连播与退出保存。
- CI 控制契约 12 项、启动失败与独立播放协调测试通过；新增契约加入默认 CI，实际 MPV
  桌面测试加入已有可选 runtime job。未触发远端 Actions。

当前测试仅覆盖生成的 SDR 样本，不代表所有 MKV/TS、HDR、高位深、声卡或多屏 DPI
已经完成验收。发布成品中的 asar 清单读取和运行库布局需随下一轮授权打包验收确认。

最终构建标识 `0.2.16 / 24525a95ed86f041`。双模式真实 Electron 报告：
`build/native-engine-SiYV1n/acceptance.json`；重试目标均为 8 秒，实际解码位置分别为
8.16 / 8.04 秒，未改变 640×360 源分辨率，源摘要不变并正常退出。同目录设置截图已目视核查。
完整独立窗口操作回归报告 `build/native-independent-2GCjdJ/acceptance.json`。
原生运行库与主流程的新边界仍保留“试用”产品提示，未宣称正式版已经交付。

## 正式交付前的剩余顺序

1. **固定可持续取得的运行库输入及完整分发材料。** 当前仍是滚动 GitHub 资产，
   `electron/mpv-runtime.json` 的 `distributionReady` 继续为 false；整理全部依赖许可、
   对应源码和构建材料后，再建立受校验的交付资源。不得仅将此布尔值改为 true。
2. **成品验收。** 在用户授权打包时，验证 EXE 与文件夹便携包的离线运行库检测、缺失/损坏
   提示、首次启动、旧数据偏好以及播放关闭。开发态通过不能替代打包态通过。
3. **硬件能力分级。** 对独立窗口补齐实际显示器、混合 DPI 与音频设备验收；内嵌叠层及
   HDR/高位深能力保持明确边界，验证前不自动启用 HDR→SDR 映射。
4. **通过门槛后再正式标记。** 移除相应“试用”提示、纳入默认分发测试；默认引擎是否调整
   应另作产品决策，不在后台改动已有用户偏好。

长时间稳定性专项继续按用户安排等待实际使用反馈，本轮不以短测代替长测。

## 第二轮：固定版本候选与交付检查

### 完成的工具改进

- `prepare-mpv.ps1` 改为调用标准库 Python 准备工具；有效缓存优先，支持 `-Offline`。
  现有 `build/mpv-download/runtime.zip` 只在摘要匹配时复用，新下载以归档摘要命名。
- 拒绝覆盖不同的现有 EXE/许可；只读取两个允许的 ZIP 成员，不全量提取注册脚本等文件。
  下载及暂存文件分别校验，原子发布不覆盖已有目标；失败回滚仅移除本次创建且身份、
  内容仍匹配的文件。对路径链接、重复成员、ZIP 符号链接、空间、下载大小和时间设限。
- 固定了当前开发运行库的完整 40 位提交。版权与关键构建/发布脚本的快照和摘要收在
  `third_party/mpv/`，没有把这些参考材料当作完整分发材料。
- `check-mpv-readiness.mjs --release` 改为检查固定标签、完整源码提交、绑定具体运行库
  的五类材料及其文件摘要；桌面/成品验收 JSON 还必须有成功结果及对应 EXE/许可摘要。
  仅把布尔值改为 true 或给出过期材料无法通过；检查不自动作许可审查结论。
- 13 项准备脚本测试、5 项发布检查测试、12 项 CI 契约通过。准备脚本测试需要 Windows
  正常的本地硬链接权限，受限沙箱下两项原子发布操作被权限阻止，正常权限重跑全部通过。

### 版本化候选的真实应用验收

从上游 [0.41.0 发布页](https://github.com/mpv-player/mpv/releases/tag/v0.41.0) 取得
`mpv-v0.41.0-x86_64-w64-mingw32.zip`，先核对资产公布的外层 SHA-256。外层是包含
另一个 ZIP 的归档，内层摘要也已固定；运行库为一个 EXE 加 23 个 DLL，共 24 个
逐文件大小/摘要记录，清单在 `ci/mpv-stable-candidate.json`。没有替换当前 `bin/mpv/`。
上游源码提交为 `41f6a645068483470267271e1d09966ca3b9f413`，构建记录为
<https://github.com/mpv-player/mpv/actions/runs/20414542745>。带版本标签仍不等于 immutable，
后续取得同名资产时仍必须核对摘要。

`AVHUB_TEST_MPV_CANDIDATE=stable-0.41.0` 仅供 Electron 测试脚本选择固定清单；
先核对双层 ZIP 和全部 EXE/DLL 的摘要、文件类型及额外文件，再在测试进程替换
`MpvClient.start` 的运行库参数，生产 IPC 没有新增路径或执行参数入口。
主应用仍验证当前开发运行库，因而这些结果是候选二进制在真实应用中的兼容验收，
**不是候选安装方案或分发链已通过**。

- `build/native-engine-G6M11G/acceptance.json`：实际设置首次启用、独立/内嵌起播、
  第 8 秒注入解码错误后重试，目标均为 8 秒；解码位置为 8.00 / 8.24 秒，正常关闭，
  640×360 原分辨率、源摘要不变。
- `build/native-independent-Sk3sBS/acceptance.json`：在同一候选下完成跳播、全屏、
  截图、倍速/字幕延迟控制、连播和退出保存/失败恢复的完整独立窗口回归。
- `npm run prepare:mpv -- -Offline` 已对当前实际缓存成功执行；随后用当前开发运行库
  重跑真实应用验收，报告 `build/native-engine-F6DJPO/acceptance.json`，确认未发生替换。

候选仍缺完整依赖许可及对应源码/构建输入。当前开发构建的上游脚本使用动态依赖输入，
不能仅根据 MPV 提交还原所有依赖。下一步应完成候选的逐依赖材料收集，随后开发匹配
24 文件布局的校验/准备流程；材料完整后才考虑授权成品验收及正式切换。
本轮没有打包、发布、升级版本或开启分发许可。

## 第三轮：多文件候选准备与源码收集

### 可重复的隔离准备流程

`npm run prepare:mpv -- -Candidate` 读取固定的候选清单，校验双层 ZIP 后仅安装清单
允许的 EXE/DLL；输出到 `build/mpv-stable-candidate/verified-runtime/`。新目录是由工具
全新提取的 24 文件精简目录，不使用原手工解压目录中的 `mpv.com` 或注册批处理。
现有默认 `bin/mpv/` 和先前手工解压目录均保留。加 `-Offline` 时只允许复用校验通过的缓存。

单文件与多文件方案共用白名单、逐文件摘要、发布前预检、空间检查和有所有权校验的失败
回滚逻辑。多文件方案额外核对大小、大小写重复文件名、未知 DLL/EXE、完整源码提交，
且拒绝把候选清单直接改成已允许分发。缓存支持旧 `runtime.zip` 与新摘要寻址归档。
CLI 的 `-Candidate` 与 `-Sources` 互斥；没有新增生产 IPC 的路径或命令入口。

### 材料进展与边界

- `third_party/mpv/candidate-components.json` 将全部 24 文件归入 16 个程序/动态组件，
  另记录构建脚本明确静态链接的 LuaJIT、MuJS，总计 18 项分类。shaderc 等的传递依赖
  还未闭合，不能将该分类称为完整 SBOM。
- 对比实际 EXE 版本输出、FFmpeg DLL 产品版本与上游提交，将 FFmpeg 的 `1fcb201`
  对应到完整提交 `1fcb201ab10cbc98d931e340da6ace292e82b1e1`。两个源码归档固定在
  `ci/mpv-candidate-sources.json`：MPV 约 7.5 MiB、FFmpeg 约 21.8 MiB，均只放在 build。
- `npm run prepare:mpv -- -Sources -Offline` 实际通过；工具核对来源 URL、完整提交、
  运行库绑定、归档摘要、大小和仓库根目录，不解压或执行源码。下载完成不等于已审查。
- `candidate-binary-versions.json` 保存逐文件摘要绑定的 Windows PE 版本资源，区分
  脚本声明版本、实际报告版本和未知准确提交。保留没有版本资源的 DLL 的空值，不猜测。
- 对应稳定提交的 MPV Copyright、GPL、构建脚本快照已有摘要记录；其他组件的完整
  许可、对应源码、构建补丁和传递依赖仍待补齐，所有许可审查状态继续 pending。

### 验证

- `test_mpv_prepare.py` 与 `test_mpv_candidate_prepare.py` 合计 27 项通过，覆盖默认
  运行库保留、多 DLL 幂等准备、双层归档、重复/路径非法成员、损坏 DLL、未知 DLL、
  缓存下载、空间不足、源码仓库/提交绑定及禁止离线联网。
- `mpv-candidate-materials.test.mjs` 检查文件全覆盖、静态依赖、源码版本绑定、快照摘要
  与 PE 版本观察；加入默认 CI。现有发布检查依然保持关闭。
- 新准备目录经过真实 Electron 验收：`build/native-engine-CGep9j/acceptance.json`，
  两种窗口模式起播与第 8 秒故障重试通过，恢复后实际位置均为 8.24 秒，保持 640×360、
  源摘要不变及正常退出。此为生成的 SDR H.264 测试，不是所有格式/硬件验收。
- `build/native-independent-eHX2mZ/acceptance.json` 与同目录 `runtime-subject.json`
  记录同一新目录下的完整独立窗口回归通过，包含跳播、全屏、截图、倍速、字幕延迟、
  连播及退出保存/失败恢复。材料/发布检查共 10 项、CI 契约 12 项通过。
- GitHub Actions 的既有手动 MPV 验证作业加入候选准备、双模式与完整独立窗口回归；
  不影响普通发布打包配置，也不会构建或发布 Release。此轮未运行远端 Actions。

下一步优先让原生启动端直接支持多文件清单的完整校验及失效检测，再收敛依赖材料与
成品布局。当前候选仍经测试钩子接入，不声明已完成正式运行库迁移或分发许可。
