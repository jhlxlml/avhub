# 播放剧集中关闭窗口卡住：退出链路修复

本轮只修改源码、构建页面与桌面壳、补回归测试，不重新打包、不改写源视频，也不处理暂缓的真实 MKV/TS 跳播调优。

## 原因

原退出逻辑等待前端保存后，先关闭媒体服务，最长等待 90 秒，最后才释放 Electron 窗口。Uvicorn 又没有 HTTP 优雅退出时间限制：仍然存活的播放器、原片 Range 或 HLS 连接可能阻止服务结束。播放窗口一直保留，形成用户可见的“关闭无反应”。剧集的结束倒计时和下一集保存回调也没有退出状态保护，退出期间仍可能切到下一集。

这是通过源码及隔离复现确认的退出链路缺陷，不代表已拿到用户当时那次卡死的日志，也不能据此归因于硬盘或视频解码。

## 修改

1. 退出开始暂停视频，冻结连播倒计时、下一条导航、迟到的切片回调与播放快捷键。退出保存由一个明确的流程负责，避免暂停和切后台重复触发进度写入。
2. 进度、设置或草稿保存失败，仍显示重试／仍然退出／取消退出，不静默丢弃数据。取消退出经 preload 通知页面，保留视频源，恢复播放及导航能力。
3. 保存完成或用户明确放弃后，先销毁播放窗口，再等待后端退出；关闭窗口不再依赖转码和视频连接完成。
4. 后端先请求暂停扫描和正常关闭；HTTP 请求分别有 1 秒、2 秒上限，正常退出等待 7 秒。超时使用 Windows taskkill /PID /T /F 终止本次启动的服务及其子进程，命令不接受页面提供的 PID，不按进程名称全局终止。
5. Uvicorn 为未结束的 HTTP 请求设置 5 秒优雅退出期限，然后进入扫描和 FFmpeg 的清理。浏览器启动模式同样采用该 HTTP 限制；Electron 另有进程树兜底。
6. 等待进程的监听器与计时器结束后清除，退出中不会重新创建窗口。网页测试服务与健康检查也增加退出期限。

以上是正常退出的限时策略，不承诺断电、系统强杀或保存失败后选择“仍然退出”能够保留最后一次修改。HTTP 请求因超时被取消时，后端日志可能包含 graceful shutdown exceeded，这与保存失败不同。

## 验证

- 前端和 Electron TypeScript 构建通过。
- 后端 81 项测试通过，新增启动端口与 HTTP 收尾限制测试。
- 退出策略测试使用两个自建 Node 进程，确认超时后父子进程都结束，并验证计时器与退出监听器清理。
- Electron 设置与退出保存测试通过，包含保存失败取消退出后，仍可用 K 恢复播放；未保存草稿不被静默提交。
- 合成剧集原生测试通过四种场景：播放中并保留一个暂停读取的原片 HTTP 连接；MKV 强制 HLS 转码并进入纯净播放；播放请求未返回；退出后再次启动并关闭。最后完整运行窗口关闭耗时约 1.8–3.1 秒，总退出约 2.1–3.4 秒（包括自动化点击及保存时间），均在测试上限内。
- 重启确认已播放剧集的进度保留，准备播放时关闭不覆盖旧进度；转码任务缓存正常回收；合成源文件大小和修改时间未变。

- 网页完整回归 106/106 通过（2.8 分钟），新增三项覆盖退出中冻结连播、取消退出后恢复快捷键和晚到的下一条保存请求。网页测试退出曾因旧健康检查无期限而挂起，已增加请求期限，最终完整运行正常结束。
- Electron 启动/退出 smoke 及窗口几何、纯净播放、置顶、比例、恢复和关闭回归通过。原生窗口测试最初直接点击已隐藏控件，按应用约定被拒绝；测试改为先模拟鼠标移动显出控制栏后完整通过，不修改“键盘不显示隐藏控件”的行为。
- 日常 `data/library.db`、便携目录 `AVHub-data/library.db` 和已有 EXE 的大小及修改时间未变。测试使用临时数据库和合成视频；不是所有真实片源、小时级播放或本次新打包 EXE 的验收。

运行退出专项回归：`npm run test:electron:shutdown`。当前已有 EXE 不会自动加载源码更新；需使用 `npm run electron:dev`，或手动重新打包后验证。
