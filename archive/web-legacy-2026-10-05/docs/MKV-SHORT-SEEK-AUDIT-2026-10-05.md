# 指定 4K MKV 的短跳播负优化核查

结论：尚未确认新版本代码造成稳定的整体退步；确认本片存在真实的慢跳点，且确认旧版鼠标焦点场景下“快进”距离不正确。不能以昨天未见提示推断昨天正确执行了同一跳转。也不能据此否定用户在实际窗口中的其他回退情况。

本轮为诊断：没有修改应用播放逻辑，没有隐藏缓冲提示，没有降低视频质量或回退快捷键修复。增加独立诊断入口，所有源视频只读，写入隔离临时媒体库与 Git 忽略的 build 报告。

## 确认的快捷键语义差异

先暂停、真实鼠标点击进度条，再按键并读取 `video.currentTime`：

| 按键 | 昨天代码 | 当前代码 |
| --- | ---: | ---: |
| → | +0.1 秒 | +5 秒 |
| L | 0 秒（未跳） | +10 秒 |
| ← | -0.1 秒 | -5 秒 |
| J | 0 秒（未跳） | -10 秒 |

原因：旧版鼠标焦点留在 range 输入上，方向键成为步长 0.1 秒的原生滑块调整，J/L 被输入控件过滤；当前正确将鼠标焦点后的按键交给播放器，并抑制重复 keyup 跳播。此修复不能回退以制造“更快”。如果用户昨天没有这个焦点条件，它不能解释用户那次观察。

报告：`focus-1791196336807.json`、`focus-1791196359205.json`。复验命令：

```
node scripts/check-shortcut-focus.mjs --source-index build/scan-benchmarks/20261003-114232-e8a18646/data/library.db --source-id 1
```

## 真正相同目标的性能对照

基准先定位 270.1 秒（不算短跳样本），随后使用真正的 →/←/L/J，循环 +5/-5/+10/-10。暂停模式固定目标，排除播放过程中时间漂移导致关键帧距离不同。以实际目标帧回调计时，不以隐藏提示或展示旧帧计时。下表中位数/最大值仅统计后面的 12 次短跳，不含首次大跨度定位。

| 条件 | 昨天 | 当前 |
| --- | ---: | ---: |
| 固定目标、逐帧像素采样，中位数 | 205 ms | 185 ms |
| 同上、最大值 | 795 ms | 996 ms |
| 关闭逐帧像素采样，中位数 | 176 ms | 177.5 ms |
| 同上、最大值 | 894 ms | 809 ms |
| 同上、出现缓冲提示的短跳次数 | 3 / 12 | 3 / 12 |

播放中（非固定目标）的一轮对照，旧版中位数 389.5 ms、当前 435 ms；当前这一轮略慢，缓冲提示次数 6→8，不能忽略。但播放时间漂移后实际跳点不同，固定目标复测并未持续恶化；没有依据将其直接定性为整体负优化。

所有测量均只有一次播放请求，源重载为 0，播放期间 FFmpeg/FFprobe 为 0。本片走原文件直放，不经过本轮新增的 H.264 批量封装调度。原文件 HTTP Range 读取主体、350 ms 提示阈值以及直放 `currentTime` 跳转方式与昨天版本相同。

低干扰对照报告：`report-1791196153189.json`（昨天）、`report-1791196071787.json`（当前）。带像素采样：`report-1791195813863.json`、`report-1791195868872.json`。播放中对照：`report-1791195517721.json`、`report-1791195578262.json`。较早旧版暂停报告 `report-1791195715143.json` 与独立 FFprobe 取帧并行，不作为主要性能对照。

## 确认存在的真实等待与待优化项

原始 packet 的关键帧位于 263.230、269.136、275.041、280.947 秒，间隔约 5.906 秒。

- 275.1 秒非常靠近关键帧，+5 跳播约 23–28 ms。
- 280.1 秒距前一关键帧约 5.06 秒，低干扰测量中旧版 +10 约 794–894 ms，当前约 760–809 ms。这时目标虽在浏览器 buffered 时间范围内，仍需要等待真实目标帧。
- 若目标已 buffered，且本次新增媒体读取为 0，仍可能有约 150–220 ms 等待。不能简单解释为硬盘或下载缓冲；encoded 数据缓存不等于目标画面已解码。
- 两版都在每次跳转截取 4K 旧帧。诊断页单独禁止该 Canvas 截取（不改应用）后，并未证明稳定的大幅帧耗时收益，同时缺画面计数增加；不能把移除遮盖层当作真实加速。

这些支持解码/关键帧距离为重要因素，但不是完整管线剖析，也不能证明某个长尾只由解码引起。

## 后续建议

1. 保留正确 5/10 秒快捷键、原画策略和真实缓冲提示，不盲目回退整版。
2. 针对实际 Electron 窗口，用相同时间点、相同按钮/键盘焦点验证，补测用户所见“昨天无提示、当前有提示”的具体条件。
3. 若连续连按造成多次 seek，中间目标可合并为最终目标，减少重复解码器重置；单次跳播不额外延迟，保持累计跳转距离和暂停意图正确。应先实验验证，再实施。
4. 4K 旧帧截取只在确有断流/黑屏风险时执行可以作为实验方向，但本轮没有足够收益证据，不提前宣称有效。
