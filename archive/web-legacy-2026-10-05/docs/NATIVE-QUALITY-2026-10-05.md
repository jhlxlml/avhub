## 画质原则与已修正路径

此前浏览器/无损 HLS 解码失败可能自动升级为视频编码；部分不兼容音轨也会自动转换为 AAC。现已收紧：

- 默认原文件直放，必要时只尝试视频 stream-copy 的封装路径；AAC 和 MP3 音轨能复制则复制，不再无谓重编码 MP3。
- 无损封装失败停止并说明原因，不自动重新编码、缩小分辨率、降低位深或 HDR→SDR。
- API 默认 `allow_video_transcode=false`、`allow_audio_transcode=false`。即使旧调用指定 `force_transcode` 或低分辨率，未明确授权也拒绝。
- 手动有损兼容/低分辨率选项会确认并明确显示有损；音频兼容可以单独授权，不能因此授权视频重编码。返回原画档撤销两种许可。
- 当前没有声称 CRF 18 或“兼容原分辨率”是无损。手动兼容仍可能变为 SDR/8-bit；只应在用户接受损失时使用。
- 原则已写入根目录 `AGENTS.md`，后续迭代也须遵守。

“保留编码/位深/HDR 信息”和“显示器最终显示一致”是不同问题；浏览器、显卡、Windows HDR 设置和显示器仍影响显示。不能据此承诺所有 HDR/Dolby Vision 文件都能完美直放。

## 可选 MKV 准备

入口：视频的 **更多操作 → 无损播放准备**。播放页打开该面板会先暂停视频；库内入口不会自动启动复制。

1. 用户明确点击开始；一次只有一个低优先级任务，不自动准备全部媒体。
2. FFmpeg 使用 `-map 0 -map_metadata 0 -map_chapters 0 -c copy`，保留所有原始轨道，在 MKV 内重建并前置 Cues，预留 2 MiB 索引空间。没有缩放、滤镜、编码器、CRF 或像素格式转换参数。
3. 前后验证轨道编码、profile、分辨率、像素格式、位深、色彩、HDR、静态/动态 HDR 配置信息、显示矩阵/比例、音轨属性、语言、disposition 和时长。源路径/大小/修改时间须保持一致。信息不符拒绝发布；不删轨、不降质补救。
4. 完成后默认音轨原片直放使用缓存；备用音轨仍从原片走既有选择路径。副本解码失败先回原文件，保留当前进度和暂停意图，不直接转码。

缓存位于应用数据目录 `native-cache/<指纹>/media.mkv`。额外占用可能接近源文件大小。总预算 8 GiB，预估源文件的 115% 加索引空间，还需预留 256 MiB 可用空间；超限/不足直接拒绝，不以降质换空间。管理器只清理已确认所有权、非源视频的已完成/终止/遗留副本，未知文件或链接不处理。当前库及保留回滚数据库引用的源路径受保护。

已打开 HTTP 读者及暂停中的 prepared 播放都有保护；面板清理遇到占用返回 409。关闭面板不取消任务；支持单独取消。恢复播放会让复制任务让路、等待空闲后从头重做，不是假称断点续传。退出停止任务，完整副本跨重启保留，源文件变化则失效。

一般存储预览单独列出副本占用；通用清理不绕过保护清理本类数据，用户在视频准备面板单独清理。

## 实片验收

使用只读复制索引 ID 1723：VP9 + Opus MKV，588.682 秒，源文件 4,111,060,107 字节，3840×2160。源文件大小和修改时间在测试前后一致；所有写入位于独立临时应用数据，不写日常媒体库。

最终报告：`build/seek-benchmark/report-1791192742673.json`（报告含本地文件名，仅保存在 Git 忽略的 build 目录）。

- 原编码、8-bit、BT.709、16:9 和 Opus 属性通过验证；副本 4,113,169,799 字节。
- 浏览器实际解码尺寸仍是 3840×2160；播放期间 FFmpeg/FFprobe 计数均为 0，只有 1 次播放请求、没有源重载。
- 首帧 244 ms，12 次跳播真实可见目标帧中位数 419 ms、P95 742 ms。跳到约 441.5 秒收到约 98.6 MB，而此前原片同目标曾读取约 2.28 GB。
- 连续播放 6 秒，实际推进约 6.16 秒，该区间缓冲提示 0；随机跳播仍有 6 次短暂缓冲提示，总计约 972 ms。没有通过隐藏提示制造“零缓冲”，也不声称完全秒跳。
- 一次较早产品复测：首帧 270 ms，跳播中位数 352 ms、P95 823 ms（`report-1791192270677.json`）。

边界：一个真实 VP9 样本不足以代表所有 MKV。原片在 E 盘，临时缓存在系统临时目录；没有清空 OS 文件缓存，生成副本也预读了源片，部分测量与测试并行，不能把全部加速归因于 Cues。最终热缓存准备耗时约 2.2 秒，较早冷一些的准备约 29.2 秒，不能承诺恒定准备速度。尚未通过同盘、同缓存和原片 Cues 解析对照证明全部瓶颈来源。

其中一次测量恰逢开发构建切换，前后端构建保护拒绝启动（`report-1791192641707.json`），没有进入视频播放，不纳入性能结果。随后构建一致复测完成。
