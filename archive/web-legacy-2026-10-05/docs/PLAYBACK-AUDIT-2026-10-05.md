# 播放启动、连续跳播与缓冲生命周期核查

构建：`e96b1ae250bec7db`。本轮改动覆盖首次打开、请求取消、播放结束回拖和首帧超时；不调整缓冲提示阈值，不降低分辨率、视频码率或转码质量参数。未打包。

## 修复

### 1. 避免明确不支持的容器先失败一次

原先每次播放都优先挂载原文件，H.264 的 TS、AVI、FLV 也如此。浏览器不能解封装时，需要等错误事件，再创建第二次播放请求。

现在先检查当前浏览器的 `canPlayType`，仅对这三类容器、且已知视频为 H.264、且浏览器返回不支持时，直接使用无损视频封装路径。画质、指定音轨和强制转码的原有选择仍生效。MP4、MOV、MKV、WebM 的原片优先策略保持不变，HEVC 仍有原片解码机会。索引不适用的回退也保留。

TS、AVI、FLV 的 UI 验收检查实际播放、一次启动请求、没有原文件失败请求以及无损封装标识。

### 2. 取消过时片段的实际封装工作

上一轮已经取消原文件的过时 Range 读取，但按需封装的 HTTP 处理仍在返回响应前同步等待 FFmpeg。浏览器连续跳播、取消旧片段时，旧 FFmpeg 和排队任务无法收到取消信号，可能挡住最后选择的位置。

分片响应现在从准备阶段开始监听断开连接。每个请求具有独立取消信号，并与会话取消信号组合；取消一个旧片段不会结束整个播放会话。等待串行锁时每 50ms 检查取消，短封装进程的取消轮询也缩短为 50ms，扫描等其他任务保持原轮询频率。50ms 是检测间隔，并非承诺进程总退出耗时。

准备线程不被直接遗弃，确保 FFmpeg 临时文件及可能已经返回的 Windows 文件句柄均能收尾。传输以 1MiB 为上限分块，断开后停止后续读取。已取消、还未发送头部的响应以 499 完成内部 ASGI 生命周期，避免中间件把正常客户端取消记成“未返回响应”的 500；真正的准备错误仍保留其 HTTP 错误状态。

### 3. 播完后可以直接回拖

原先 `ended` 事件立即删除后台会话，但前端还保留完整 HLS 时间轴。回拖到已经不在浏览器缓存中的位置时，会请求不存在的会话，造成重新准备或错误；播放结束覆盖层也可能未退出。

现在播放页仍打开时保留有容量限制的会话与心跳。回拖退出结束状态、取消自动下一条倒计时，并复用当前源。返回媒体库、关闭页面、切换视频仍清理会话。直接播放、TS 索引直读、索引按需封装均验证了真实播放到结尾后回拖、暂停目标帧、恢复播放及退出清理。

### 4. 首帧未到达时仍有超时保护

原先收到 `loadedmetadata` 就撤销浏览器载入超时，即使仅有元数据、一直没有画面，也可能无限等待。现在需要已有视频画面数据和有效尺寸才撤销这一超时。45 秒上限及正常缓冲提示阈值未改。

## 画质与实测

原片直放传输源字节；TS 索引直读返回原 TS 包；索引封装继续使用 `-c:v copy`。现有回归比较封装片段与原视频的解码像素、首关键帧和尺寸，包含 B 帧、长 GOP、AVI 时间戳重建及非零起点。没有使用缩小画面、减少视频码率或跳到附近关键帧的方式提速。音频不兼容时仍可能单独转 AAC。

所有实际样本只读，从先前复制的索引选取；测试使用临时媒体库。MKV/AC3 对照由真实 MOV 在临时目录复制视频编码生成。记录目标帧真实呈现且保持层已撤下的 `visibleMs`，不是缓冲文字消失时间。每轮 12 个交错目标；此样本量的 P95 实际为本轮最大值。操作系统文件缓存未清空，表中不同轮差异不等于纯代码收益。

| H.264 / MP4，4K，原片 | 446ms | 173ms | 299ms | 0 |

原片 MP4 的 H.264、AV1 第一跳仍采样到片头暗画面，上一轮已验证这些源含黑场/淡入。本轮各成功轮次没有采样到“既无当前数据、也无保持层”的可见区间；按帧采样不表示绝对不会出现更短闪烁。

### TS 首次打开对照

同一个约 2.5GB、17 分钟的 4K TS：强制模拟旧版先尝试原文件，第一轮首画面 17286ms、两次启动请求；新路由首画面 1961ms、一次请求。随后重新跑旧路由，首画面为 2030ms、仍为两次请求。因此 **不能把 17.3 秒到 2 秒全部归因于本次代码**，第一轮文件缓存等因素明显影响结果。已确认的改善是省掉必然失败的原文件尝试和一次完整启动流程；首次完整关键帧索引成本仍然存在。

### MKV 连续改选位置对照

同一真实画面生成的 H.264/MKV/AC3，每个最终目标前以 40ms 间隔发送三个不同的跳播目标，12 组共 48 次操作。仅在基准服务器内关闭请求级取消作为旧行为对照，视频编码与客户端相同。

| 行为 | 最终目标中位数 | P95 / 最大值 | 记录到的缓冲提示 | 源重载 |
| --- | ---: | ---: | ---: | ---: |
| 旧请求继续封装 | 181ms | 380ms | 4 | 0 |
| 过时请求取消 | 208ms | 242ms | 0 | 0 |

该轮改善了最慢等待，中位数没有改善，不能宣称每次跳播都加速。缓存复用、进程启动和解码器都会影响结果。单元测试另通过受控阻塞确认：取消旧请求能释放队列、已取消的排队请求不会运行编码器、后续请求可成功获取原编码片段、会话不被误取消。

## 保留的限制

- 4K VP9/MKV 仍有约 4 秒的长尾；直接播放没有重建源，浏览器寻址和解码仍有成本，未通过有损转换换取较快响应。
- 当前浏览器不能解码的 HEVC 仍需兼容转码，且未生成目标位置时会重建播放窗口。本轮短样本仍有 12 次跳播重载，未声称解决。
- 兼容转码不等于无损，保留分辨率也不等于原编码无损。本轮没有降低其既有质量参数。
- 长 HEVC、HDR/10-bit 的真实样本不足，继续保留未验证项。
- 初次建立完整索引仍需读取源文件；网络盘、超长文件、损坏时间戳的启动成本并未消失。

## 验证与复现

前端构建通过。后端完整回归 231 项：230 通过、1 跳过；随后针对取消响应收尾的 9 项媒体传输测试再次通过。UI 首批 25 项通过，取消响应修正后索引封装及稳定性 43 项通过；两批含 7 项重复用例，共覆盖 61 项不同用例。后批没有再出现取消导致的 `No response returned` 500。
